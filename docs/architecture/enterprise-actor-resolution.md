# Enterprise Actor Resolution & Supply-Chain (Part Catalogue) Workflow — architecture baseline

Status: implemented for Part Catalogue (migration `20261007201434_EnterpriseActorResolution`). Reusable by any workflow.

## 1. Principle

`PEMS.WorkflowPlatform` (`IWorkflowRuntime`) is the single workflow engine and system of record.
Enterprise Actor Resolution is an **actor-resolution subsystem consumed by the engine through a hook**; it never executes a workflow.

```
Business object (PartCatalogueRequest)      [EXISTING]
   └─ facts via IWorkflowBusinessContextProvider (IsNewManufacturer, CommodityGroup1Id, ...)   [NEW, module-neutral contract]
WorkflowStage (ResponsibilityKey, EntryCondition)                                              [EXTENDED additively]
   └─ EnterStageAsync (runtime): EntryCondition → IWorkflowActorResolutionHook                 [NEW hook]
        └─ ActorResolutionWorkflowHook → IEnterpriseActorResolver (Persistence)                [NEW]
              Responsibility (WorkflowActorResponsibility + Positions)                          [NEW config]
              Position → EmployeeAssignment (validity, one holder per seat)                     [REUSE]
              Role (AspNetUserRoles) + permission (IRoleModuleActionService)                    [REUSE]
              Scope: Department | Discipline | MaintenanceGroup | Team                          [REUSE entities]
              Commodity: CommodityGroupResponsible → Position / audited employee override      [NEW config]
              Reporting line: PartCatalogueOrgLink (+ CEO skip)                                 [REUSE]
              SoD (requester excluded), active employee, queue / single-actor selection
   └─ WorkflowInstanceStage + WorkflowInstanceStageCandidate (immutable snapshot + JSON why)   [NEW]
ExecuteActionAsync: actor must be a *selected snapshot candidate*; initiator denied; no role/admin bypass
   └─ transition RequiredPermission via IWorkflowAuthorizationHook (existing) + ForbidInitiator
WorkflowHistory (existing audit)  +  PartCatalogueRequestApproval (module print/audit projection)
```

## 2. Concepts (kept separate)

| Concept | Meaning | Where |
|---|---|---|
| Role | permission bearer | Identity roles (unchanged) |
| Position / EmployeeAssignment | organizational seat and current holder (one active holder per seat) | existing org structure UI (Team page) |
| Scope | where the responsibility applies | `ScopeType/ScopeValue` on the responsibility |
| Commodity group | which specialist | `CommodityGroupResponsible` (group → position, optional employee override) |
| Responsibility | business accountability of a stage (e.g. `MaintenanceSupervisor`) — **not** an Identity role | `WorkflowActorResponsibility` |

`MaintenanceSupervisor`, `SparePartsSpecialist`, `CommodityGroupReview`, `PartCataloguer` are workflow responsibilities. No Identity roles were created.

## 3. Diagnostic states

`RESOLVED`, `MULTIPLE_ELIGIBLE_ACTORS`, `NO_CONFIGURATION`, `NO_ELIGIBLE_ACTOR`, `REQUESTER_ONLY`, `INACTIVE_ACTOR`, `WRONG_ORGANIZATION_SCOPE`, `WRONG_COMMODITY_SCOPE`, `MISSING_PERMISSION`, `NOT_APPLICABLE` (stage skipped, e.g. direct manager is the CEO).
Ordinary users see a safe message (`Pc_Route_NoEligibleApprover`); `PartCatalogue.Admin` sees the state (`Pc_Route_State_*`). Admin page: per-responsibility "Diagnose" lists eligible and excluded people with the reason, plus data-quality findings.

## 4. Determinism and history

- Queue (default): every eligible candidate may act; first decision completes the stage.
- SingleActor: order = position priority, then lowest `EmployeeId`. No unordered `FirstOrDefault` is used for actor selection.
- Commodity: Group 1 first; Group 2 only if Group 1 has no responsible.
- Candidates are snapshotted when the stage is entered; later transfers do not change who could act or the history.
- Resolution failure on stage entry throws `WorkflowActorResolutionException` before anything is saved (fail-closed). Submit pre-validates the whole applicable route.

## 5. Engine changes (additive, backward compatible)

`WorkflowStage.ResponsibilityKey/EntryCondition`; `WorkflowInstanceStage.ResolutionState/ResolutionDetails/ResolvedDate/Candidates`; table `WorkflowInstanceStageCandidates`;
`IWorkflowActorResolutionHook`, `IWorkflowBusinessContextProvider`; evaluator accepts module fields; a `Return` that ends an instance sets status `Returned`.
Stages without `ResponsibilityKey` behave exactly as before.

## 6. Part Catalogue migration

New submissions run on the shared engine (workflow "Part Catalogue Request Approval", binding `PartCatalogue/PartCatalogueRequest/Approval`), generated by `PartCatalogueWorkflowSeeder` from the *current* `PartCatalogueWorkflowSteps` (order/active/condition as edited by admins).
`PartCatalogueRequestStep` / `PartCatalogueRequestApproval` are now projections for UI/print. `PartCatalogueRoutingPlanner`, `PartCatalogueApproverAssignment` (pool source) and `PartCatalogueOrgLink` remain: planner/legacy `ExecuteAsync` path are **DEPRECATED** and used only for requests with `WorkflowInstanceId = null`.
Seeded responsibilities default to the legacy pool source so existing configuration keeps working; admins switch each to Position / Commodity sources.

## 7. Known limits / decisions

- No admin approval override on the engine path (admins may cancel with a comment). Legacy requests keep the old override.
- Acting assignments are not implemented: the unique active-assignment-per-position index forbids two active holders.
- Warehouse scope is not supported: PEMS has no employee↔warehouse relation.
- Stages are edited in the workflow designer (versioned); the Admin page shows them read-only.
- Reporting-line (direct/superior manager) data still lives in `PartCatalogueOrgLinks`.

## 8. Organization hierarchy as the only manager source (Phase 1)

`RequesterManager` responsibilities (`ManagerLevel` 1 = Direct Manager, 2 = Superior Manager, N = N-th ancestor) resolve **only** through `OrganizationManagerChain`: Employee → primary effective assignment → `Position.ParentPositionId` chain → effective holder. Position ≠ Role ≠ Permission; Team Supervisor and Department are never manager sources; there is no CEO/Admin fallback. Structural problems return `ORGANIZATION_RESOLUTION_REQUIRED` + issue code and an explainable `ResolutionPath`; consuming modules decide how to wait (Part Catalogue: status `OrgResolution` + Retry). Maintenance, validation and import of the hierarchy: `Admin/Organization`, `Admin/Organization/Diagnostics`, Import Center → Organization Structure Import.
