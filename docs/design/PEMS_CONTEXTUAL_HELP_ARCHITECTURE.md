# PEMS Contextual Help Architecture (Design — Not Implemented)

**تاریخ:** 2026-09-13
**وضعیت:** Design-only. هیچ Entity، Migration، Controller، یا View در این سند ساخته نشده -
طبق محدودیت صریح دامنه‌ی فاز ۲B. این سند پیش‌نیاز `docs/audits/PEMS_PHASE2B_INFORMATION_ARCHITECTURE_AUDIT.md`
بخش‌های ۶-۹ را دارد؛ همان یافته‌ها این‌جا تکرار نمی‌شوند، فقط به آن‌ها ارجاع داده می‌شود.

---

## ۱. اصل راهنما

طبق یافته‌ی ممیزی (بخش ۶): سیستم Help در PEMS کاملاً Greenfield است - هیچ چیزی برای گسترش
وجود ندارد، فقط باید از صفر طراحی شود. اصل راهنمای این طراحی: **کوچک، افزودنی، جدا از
Workflow.** هیچ جدولی که این سند پیشنهاد می‌دهد نباید FK به هیچ موجودیت Workflow-Critical
(Document، Revision، Approval، Transmittal، WorkOrder) داشته باشد - Help باید بتواند کاملاً
حذف شود بدون این‌که هیچ داده‌ی کسب‌وکاری آسیب ببیند.

## ۲. معماری Contextual Help (پیشنهادی)

سه لایه‌ی مجزا، هرکدام با هدف متفاوت:

```
لایه ۱ — Tooltip (موجود، فقط استفاده‌ی گسترده‌تر)
   window.PemsTooltips + data-bs-toggle="tooltip" + title="..."
   → توضیح یک‌خطی یک فیلد/دکمه/آیکون، بدون نیاز به داده‌ی دیتابیس

لایه ۲ — Inline Help Hint (جدید، سبک)
   یک آیکون "؟" کوچک کنار عنوان بخش/فرم → روی کلیک، یک Popover کوتاه (۲-۳ جمله) باز می‌شود
   → از همان HelpTopic زیر می‌آید، ولی فقط خلاصه (Summary) را نشان می‌دهد

لایه ۳ — Help Article / Panel (جدید، کامل)
   یک Drawer/Panel سراسری (نه Modal - چون کاربر باید بتواند همزمان به فرم زیرش نگاه کند)
   → محتوای کامل (Content)، لینک‌های "Related Topics"، و دکمه‌ی "Learn More" برای مستندات عمیق‌تر
```

این سه‌لایگی مستقیماً به سؤال «Tooltip در برابر Help Article» (بخش ۳) پاسخ می‌دهد: این دو
رقیب هم نیستند، سه پله‌ی پیش‌رونده‌ی یک مدل واحدند.

### مدل داده‌ی پیشنهادی (فقط طراحی - STOP قبل از پیاده‌سازی)

```
HelpTopic
- HelpTopicId (PK)
- ModuleKey        (string, مثلاً "EngineeringDocuments", "VDR", "Permit" — باید دقیقاً با
                     نام Controller یکی باشد تا Resolve خودکار ممکن شود، نه یک رشته‌ی آزاد جدا)
- RouteKey         (string nullable — مثلاً "Details"، "Create" — برای Help مخصوص یک اکشن،
                     نه کل ماژول؛ null یعنی «راهنمای کلی ماژول»)
- FieldKey         (string nullable — برای Inline Hint روی یک فیلد خاص فرم، مثلاً
                     "ConfidentialityLevel"؛ اگر پر باشد، ModuleKey+RouteKey+FieldKey با هم
                     منحصربه‌فرد است)
- TitleEn / TitleFa
- SummaryEn / SummaryFa      (۱-۲ جمله — همان‌که در Popover لایه‌ی ۲ نشان داده می‌شود)
- ContentEn / ContentFa      (Markdown یا HTML محدود — محتوای کامل لایه‌ی ۳)
- LearnMoreUrl               (nullable — بخش ۶)
- RelatedTopicKeys           (JSON array از HelpTopicId‌های دیگر، یا نگاشت به ModuleKey — برای
                               «موضوعات مرتبط» در پایین Panel)
- Keywords                   (nullable, برای جست‌وجوی درون Help — بخش ۷ سند سوم)
- IsPublished                (bool — پیش‌نویس در برابر منتشرشده؛ یک ادمین محتوا باید بتواند
                               بدون کد جدید، محتوا اضافه/ویرایش کند)
- CreatedDate / ModifiedDate / ModifiedBy   (طبق `BaseEntity` موجود پروژه، برای یکدستی)
```

**چرا این شکل و نه شکل دیگر:** `ModuleKey`+`RouteKey`+`FieldKey` دقیقاً با همان کلیدهایی
مطابقت دارد که `IPermissionService.HasPermissionAsync(roles, module, action)` از قبل استفاده
می‌کند (`module` = `ModuleKey`) - یعنی Resolve کردن «کدام HelpTopic باید در این صفحه نشان
داده شود» می‌تواند از همان `ViewData`/Route Value موجود در هر Controller استفاده کند، بدون
نیاز به یک مکانیزم Registration جداگانه.

## ۳. قاعده‌ی Tooltip در برابر Help Article

| معیار | Tooltip (لایه ۱) | Inline Hint (لایه ۲) | Help Article (لایه ۳) |
|---|---|---|---|
| طول محتوا | ≤ ۸ کلمه | ۱-۳ جمله | نامحدود (چند پاراگراف) |
| محل ذخیره | صفت `title` در خودِ View (Hardcoded) | `HelpTopic.SummaryEn/Fa` | `HelpTopic.ContentEn/Fa` |
| هدف | «این دکمه/آیکون چیست؟» | «این بخش/فیلد چه‌کاری می‌کند؟» | «چرا این فیلد این‌طور رفتار می‌کند؟ + مثال + پیوند به رویه‌ی کامل» |
| نیاز به بیلینگوال دیتابیسی | نه (چون یا آیکون است یا یک برچسب کوتاه که از `SharedResource.resx` می‌آید) | بله | بله |
| نیاز به Migration | نه | بله (همان جدول لایه ۳) | بله |
| مثال واقعی موجود | `title="SHA-256: ..."` در EDMS | (وجود ندارد - جدید) | (وجود ندارد - جدید) |

**قاعده‌ی تصمیم‌گیری ساده برای توسعه‌دهنده‌ی آینده:** اگر محتوا با تغییر زبان UI (نه فقط
یک برچسب، بلکه توضیح واقعی کسب‌وکاری) نیاز به ترجمه دارد و بیش از یک جمله است → هرگز در
`title="..."` خام ننویس، همیشه از `HelpTopic` بیاید.

## ۴. تفاوت با `KnowledgeBaseController` (رفع ابهام نام‌گذاری)

طبق یافته‌ی ممیزی بخش ۶، این دو باید کاملاً مجزا بمانند تا سردرگمی کاربر/توسعه‌دهنده پیش
نیاید:

| | `KnowledgeBaseController` (موجود) | Help System (پیشنهادی) |
|---|---|---|
| محتوا | مدارک مهندسی واقعی آپلودشده (Embedding) | راهنمای نوشته‌شده‌ی دستی درباره‌ی خودِ نرم‌افزار |
| مخاطب | «این پروژه کجا درباره‌ی X تصمیم گرفته؟» | «این صفحه/دکمه/فیلد چه‌کاری می‌کند؟» |
| منبع محتوا | خودکار (AI Extraction از مدارک) | دستی (نویسنده‌ی محتوا/مالک محصول) |
| پیشنهاد نام‌گذاری UI | «Knowledge Base» / «AI Search» (بدون تغییر) | «Help» یا «راهنما» (هرگز «Knowledge Base») |

## ۵. مدل دوزبانه‌ی Help

طبق یافته‌ی ممیزی بخش ۸، محتوای Help **نباید** در `SharedResource.resx` جا بگیرد (آن فایل
برای برچسب کوتاه UI است، نه پاراگراف). به‌جای آن:

- هر `HelpTopic` مستقیماً هر دو ستون `...En`/`...Fa` را در همان ردیف دارد (نه یک جدول
  Localization جدا) - این ساده‌ترین مدل برای محتوایی است که به‌ندرت تغییر می‌کند و تعداد
  زبان‌هایش برای مدت طولانی همان ۲ زبان امروز (`en`/`fa`) باقی می‌ماند؛ اگر PEMS در آینده
  زبان سوم اضافه کند، آن زمان مهاجرت به یک جدول `HelpTopicTranslation(HelpTopicId,
  CultureCode, Title, Summary, Content)` منطقی‌تر می‌شود - **امروز آن پیچیدگی را اضافه
  نکنید.**
- انتخاب زبان محتوای نمایش‌داده‌شده دقیقاً از همان کوکی موجود (`CookieRequestCultureProvider`)
  می‌آید - بدون منطق جدید.
- **قانون سخت‌گیرانه:** اگر `ContentFa` برای یک ردیف خالی باشد، UI باید صریحاً بنویسد
  «ترجمه‌ی فارسی هنوز موجود نیست» و `ContentEn` را نشان دهد - هرگز نباید سکوت کند یا خالی
  رندر شود؛ این از همان اصل «هیچ‌وقت رفتار سخت‌گیرانه‌تر از واقعیت وانمود نشود» پیروی می‌کند
  که در ممیزی فاز ۱ برای Command Bar هم رعایت شده بود.
- تاریخ‌های `CreatedDate`/`ModifiedDate` روی `HelpTopic` باید از همان قرارداد میلادی-اجباری
  پیروی کنند (بخش ۸ ممیزی) - بدون استثنا.

## ۶. رفتار RTL/LTR برای محتوای Help

- خودِ Panel/Drawer/Popover باید فقط از خاصیت‌های منطقی CSS استفاده کند
  (`inset-inline-start` به‌جای `left`، `margin-inline-end` به‌جای `margin-right`) تا با
  تغییر `dir` روی `<html>` (طبق بخش ۹ ممیزی) بدون نیاز به یک برگه‌ی RTL اختصاصی جدید، خودکار
  Flip شود.
- محتوای `ContentFa` که از راست به چپ نوشته می‌شود باید داخل یک Container با
  `dir="auto"` یا `dir="rtl"` صریح رندر شود - **مستقل از این‌که کدام زبان UI انتخاب شده**؛
  یعنی اگر کاربری زبان UI را `en` گذاشته ولی به هر دلیلی محتوای فارسی را می‌بیند (حالت
  Fallback بخش ۵)، آن بلوک محتوا باید خودش RTL باشد، نه کل صفحه.
- کدهای نمونه/دستورات فنی داخل محتوای Help (اگر باشد) همیشه باید `dir="ltr"` صریح داشته
  باشند، حتی داخل یک بلوک فارسی - این یک قاعده‌ی استاندارد بین‌المللی‌سازی است، نه یک تصمیم
  خاص PEMS.

## ۷. Learn More Deep-Linking

`HelpTopic.LearnMoreUrl` یک URL اختیاری برای پیوند به مستندات عمیق‌تر (رویه‌ی رسمی PDF، یک
سند در `docs/`، یا در آینده یک پورتال مستندات جدا) است:

- **قانون امنیتی:** این فیلد هرگز نباید مستقیماً در یک `<a href>` بدون بررسی رندر شود اگر
  از یک منبع غیرقابل‌اعتماد (ورودی کاربر عادی) بیاید - چون این یک فیلد مدیریت‌شده توسط
  مالک محتوا/ادمین است (نه کاربر نهایی)، ریسک XSS پایین است، اما رندر باید همچنان از
  `UrlHelper`/Razor Encoding استاندارد استفاده کند، نه `Html.Raw`.
- **قرارداد Deep-Link داخلی:** وقتی `LearnMoreUrl` به یک صفحه‌ی دیگر PEMS اشاره می‌کند
  (نه یک URL بیرونی)، باید از یک قرارداد نسبی و پایدار استفاده کند
  (`/Help/Topic/{ModuleKey}/{RouteKey}`) - **نه** یک ID خام دیتابیسی در URL، تا اگر محتوا
  بازسازی/Re-seed شد، لینک‌های قدیمی (مثلاً از یک PDF چاپ‌شده یا یک ایمیل قدیمی) نشکنند.
- در صورت باز نبودن لینک (۴۰۴)، باید کاربر را به یک صفحه‌ی Help عمومی (فهرست موضوعات
  ماژول) هدایت کند، نه یک خطای خام - همان الگوی `NotFound()`/Redirect دوستانه که در سراسر
  PEMS برای موجودیت‌های گم‌شده استفاده می‌شود.

## ۸. Resolve شدن خودکار Help در هر صفحه (طرح مفهومی، نه پیاده‌سازی)

هر Controller از قبل `ViewData["Section"]`/`ViewData["Title"]` را ست می‌کند (طبق
`_Breadcrumb.cshtml`). پیشنهاد: یک `ViewComponent` سبک (`HelpHintViewComponent`) که
`RouteData.Values["controller"]` جاری را به‌عنوان `ModuleKey` می‌گیرد و اگر یک `HelpTopic`
منتشرشده برای آن ماژول/اکشن پیدا شود، آیکون «؟» را رندر می‌کند - در غیر این صورت هیچ‌چیز
رندر نمی‌کند (بدون شکستن صفحاتی که هنوز محتوای Help ندارند). این دقیقاً همان الگویی است که
`_Breadcrumb.cshtml` امروز بدون شرط رندر می‌شود؛ Help باید شرطی باشد چون محتوا تدریجی
پر می‌شود.

## ۹. آنچه عمداً از این طراحی بیرون گذاشته شد

- **بدون CMS کامل.** هیچ ویرایشگر WYSIWYG جدید، هیچ گردش‌کار انتشار/تأیید محتوا در این فاز
  طراحی نشد - اگر حجم محتوا زیاد شود، فاز جداگانه‌ای لازم است؛ برای شروع، مقادیر اولیه
  می‌توانند مستقیم با Migration Seed شوند (دقیقاً مثل الگوی `PermissionService.SeedDefaultsAsync`
  که در فاز امنیتی این جلسه استفاده شد).
- **بدون جست‌وجوی اختصاصی Help در این سند** - رابطه‌ی Help با Global Search در سند سوم
  (`PEMS_PORTAL_INFORMATION_ARCHITECTURE.md`) بحث می‌شود، چون به معماری Search فاز ۲A
  وابسته است.
- **بدون تحلیل Analytics/"چند نفر این مقاله را خواندند"** - خارج از دامنه‌ی این فاز و
  نیازمند تصمیم مالک محصول درباره‌ی حریم خصوصی/رهگیری.

## ۱۰. پیش‌نیاز پیاده‌سازی (وقتی این طرح تأیید شد)

1. تأیید مالک محصول روی شکل `HelpTopic` (بخش ۲).
2. یک Migration واحد و کاملاً افزودنی (بدون FK به هیچ جدول Workflow-Critical).
3. `HelpTopicService`/`IHelpTopicService` در `PEMS.Application`/`PEMS.Persistence` طبق الگوی
   موجود پروژه (نه منطق کسب‌وکار در Controller).
4. `HelpHintViewComponent` + یک Partial `_HelpPanel.cshtml` که از `window.PemsTooltips`
   برای لایه‌ی ۱ و یک Bootstrap Offcanvas (نه Modal) برای لایه‌ی ۳ استفاده می‌کند.
5. Seed حداقلی برای یک ماژول پایلوت (پیشنهاد: Engineering Documents - طبق بخش ۴ سند ممیزی،
   چون از قبل پخته‌ترین IA را دارد و بیشترین سود از یک Help متمرکز می‌برد).
6. تست‌های واقعی طبق الگوی این نشست (Seed واقعی + Assert روی رفتار Fallback زبان + رفتار
   IsPublished=false).

هیچ‌کدام از این ۶ قدم در این فاز اجرا نشد.
