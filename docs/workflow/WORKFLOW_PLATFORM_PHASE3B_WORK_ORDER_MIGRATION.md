# Workflow Platform — Phase 3B: Work Order Migration

**Classification: ACCEPTED WITH DOCUMENTED LIMITATIONS** (limitations in §24)

## 1. Scope and outcome
Work Order lifecycle (Created → Maintenance Planning → Preparation / Assignment → Operations Issue / Release → In Execution → Completion → Originating-Discipline Verification → Final Approval → Closed, with On Hold / Cancelled / Rejected as workflow transitions) is governed by the central Workflow Platform through an explicit, version-pinned binding. `WorkOrder.Status` is a projection of the current stage. No new workflow engine, history store or authorization framework was created.

## 2. Workflow definition, binding and versioning
* Definition `Work Order Lifecycle` (module `WorkOrder`, entity type `WorkOrderLifecycle`, context `Standard`), seeded by `WorkOrderLifecycleWorkflowSeeder`; published version 1, immutable after publication (platform guard).
* Explicit binding → pinned version. New Work Orders start an instance on the bound version; existing instances stay on their version.
* Multi-discipline review is a **separate** process (`WorkOrderMultiDisciplineReview`, Architecture A) with its own binding/identity (`WorkOrder|WorkOrderLifecycle|{id}` vs `WorkOrder|WorkOrderMultiDisciplineReview|{id}`).

## 3. Work order types
Exactly four: Preventive, Corrective, Predictive, Emergency. No Shutdown/Turnaround. Emergency has **no** bypass (verified in unit tests and browser).

## 4. Organizations and identity
`Department.OrganizationDomain` (Engineering / Maintenance / Operations / Warehouse; inherited from the parent department; seeder back-fills by department name) + `Employee.DisciplineId`. Engineering/Mechanical ≠ Maintenance/Mechanical (organization is part of the identity check). Warehouse has no workflow authority. Unknown domain fails closed.

## 5. Originating vs responsible discipline
`WorkOrder.OriginatingOrganization / OriginatingDisciplineId / OriginatingRequestedById` are snapshotted at creation (or at Work Request conversion) and never replaced. `ResponsibleOrganization / ResponsibleDisciplineId` are set in Maintenance Planning. Verified end-to-end: an Engineering-origin Work Order converted from a Work Request stayed Engineering-origin, was executed by Maintenance/Mechanical, verified by Engineering/Mechanical and final-approved by an Engineering supervisor.

## 6. Authorization
`WorkOrderAuthorizationHook` composes on top of `AccessControlWorkflowAuthorizationHook` (existing `IAccessControlService`), adding organization/discipline rules per task permission (`WorkOrder.Plan/Prepare/Assign/Issue/Execute/Hold/Verify/FinalApprove/Reject/CancelPreIssue/CancelExecution`). Permission-based pseudo-role participants are expanded by the module service. `WorkOrderGovernanceSeeder` (one-time, marker-guarded, deactivate-not-delete) removes the pre-3B broad Create/Edit/Approve/Execute authority from the legacy engineering roles.

## 7. Separation of duties (server-side)
Creator ↔ Executor **allowed**. **Denied:** Planner = Executor, Operations Issuer = Executor, Executor = Verifier, Verifier = Final Approver, Creator = Closer. Manager/deputy may Cancel/Reject but cannot final-approve what they executed/verified. Enforced from `WorkflowHistory` prior actors keyed by transition permission; UI shows the denial reason, the server re-checks (forged POST tests).

## 8. Domain rules kept in the Work Order domain
Responsible discipline required before completing planning; team/executor required before requesting issue; executor must be Maintenance and in the responsible discipline; Operations release gate (permit/LOTO/gas test); ISO 14224 failure fields required for Corrective/Emergency; running multi-discipline review blocks completion; cancelling a Work Order cancels its open review; maintenance history / failure record on completion.

## 9. Status projection
Stage `BusinessStatus` projects onto `WorkOrder.Status` (Open, Assigned, InProgress, OnHold, Completed, Closed, Cancelled, Rejected) in the same save as the transition. List/KPI/report consumers of the status column are read-only projection consumers (§17).

## 10. Legacy Work Orders
No backfill. Records without a lifecycle instance stay legacy and keep the previous status buttons. Cutoff = earliest lifecycle binding creation date; a post-cutoff ungoverned Work Order (e.g. generated by PM / instrument paths) is refused on the legacy path and adopted by `GovernPendingNewAsync`. The 3 existing PEMSDB Work Orders and the running legacy review (instance 74) are untouched.

## 11. Concurrency and idempotency
One running lifecycle instance per Work Order (filtered unique index, migration `WorkflowInstanceRunningUniquePerEntity`); `WorkflowConcurrencyConflictException`/`DbUpdateConcurrencyException` become bilingual conflict messages; create + start + audit are one transaction. User transactions run inside the execution strategy (§21 — defect found and fixed during QA).

## 24. Documented limitations
* No admin UI to set `Department.OrganizationDomain`; it is derived from department name/parents by the seeder (unknown → fail closed). Departments outside the four names need a manual value.
* Engineering-origin Work Orders arise only via Work Request conversion (Engineering has no Create authority by design); in browser QA that conversion was invoked through the real `IWorkRequestService`, not through the Work Request UI.
* Issuer≠Executor and Manager-executed/verified≠Final-approver SoD rules were verified by unit tests; the browser exercised the Planner, Executor, Verifier and Creator rules and Manager cancel/reject.
* Some pre-existing hard-coded English strings on the Work Order page (`Started:`, `Completed:`, several badges/labels, multi-discipline and labor hints) remain untranslated in FA; not introduced by this phase.
* Participant text under the current stage shows permission codes (`WorkOrder.Verify`) rather than friendly role names.
* `SetPlanning`/`AssignExecutor` forms remain visible in later Assigned-status stages; server rules govern.
* Transient SQL faults inside a user transaction are reported as a failure message rather than retried (caught by the module's `DbUpdateException` handler).
