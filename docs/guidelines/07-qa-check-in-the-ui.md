# 07 - QA check in the UI (after the merge, while the task is In Review)

Owner decision 2026-10-26. Read it when you move a task to In Review, when you are asked to QA a task, and when you review a pull request.

**In Review = conditional done**: the author verified the work as far as the session allows, the PR is **merged into `main`**, and the tests are either green or listed as not run (section 2a) ([chapter 00](00-task-lifecycle.md) section 4). **QA check = an independent
person confirms it in the real user interface of what is now on `main`, before Done.** Automated tests (chapter 01) and this check complement each other; **for now they are one step** (section 2a): the test run is line 1 of the checklist.
Instructions rules 13 (no Done without evidence) and 14 (a row whose Test Plan status is "Needs QA" is not trustworthy) are what it serves.

## 1. Flow

`In Progress` -> author finishes, runs the tests if the session can, PR open -> **merge into `main`** -> **`In Review` + label `qa-pending`** (right after the merge) -> QA check (this chapter) ->
`qa-passed`: `Done` | `qa-failed`: back to **`To Do`** with the defects listed (owner decision 2026-10-26); whoever takes it up moves it to In Progress, the fix goes through a new branch and PR to `main`, then In Review again.

**Timing (owner decision 2026-10-27):** the author does not wait for this check. The author hands over with `In Review` + `qa-pending` and a test note ("Tests: passed" with counts, or "Tests: not run / not done" with the reason), then continues with the next task. The QA checks are run by someone else, as a block at the end of the sprint once all sprint tasks are In Review; Done comes only from that verdict.

Labels: `qa-pending`, `qa-passed`, `qa-failed` (one at a time; the author sets `qa-pending` when moving to In Review after the merge, the tester replaces it).

## 1a. Entering and re-entering In Review (author's duty)

Whoever moves the issue to In Review - the first time **and every time after a failed QA** - checks, in this order, and says so in the move comment:

1. **QA checklist present.** The issue has a Jira comment "QA checklist" (template in section 5) with line 1 = local tests, one line per *Done when* item, the standard lines, and the **how to test** as references to the README sections of section 5a (never copied steps). The author drafts it; the tester completes and runs it.
2. **Test note present, and the test lines marked.** The checklist contains the task's automated tests as lines and the author's results are posted as "QA checklist - author results" (section 5): `Pass (author, date)` for what ran, `not done - reason` for the rest. The move comment has a "Tests" paragraph: the commands that were run with their counts, or the exact commands that were **not** run and why (section 2a). Docs-only tasks say "n/a (docs only)" and name the read-through of section 6.
2a. **Not-run lines present** (section 1b): the SQL Server tests, the HTTP smoke tests and the browser check appear as lines marked `not done - <reason>` whenever the author did not run them.
3. **README up to date.** Any new manual check or local test of this task is already in the right existing README (section 5a) and the checklist refers to it.
4. **Re-entry after `qa-failed`** (the issue came back through To Do): do not edit or delete the earlier checklist. Re-check it against the new commit and add a new comment "QA checklist - round N" with: every failed line to retest, one regression line per defect (Bug keys), lines for the areas the fix touched, and two neighbouring checks; update the Tests paragraph with the new commit and counts; replace `qa-failed` by `qa-pending`.
5. If one of these is missing the issue is not ready: the tester starts nothing, marks the checklist line "Blocked: no QA/test note" and asks the author (the issue does not count as In Review for planning until fixed).

## 1b. Nothing that was not run lives only in a message (owner decision 2026-10-27)

Jira is the only place a tester, or an agent that has no access to the chat, can read. Therefore:

- **Every test, check or step the author did not run is a line of the QA checklist** with the result `not done - <reason>` (never a sentence only in the move comment, the PR or the chat). The line names the exact command or the README check ID, so it can be run without asking.
- **The standard "not run" lines** a cloud-session author adds unless they really ran them: (a) the tests that need SQL Server: `dotnet test PEMS.slnx` (full suite), with the known failures of README.md "Local tests"; (b) the HTTP smoke tests (`FileSecurityHttpTests` and the other tests that start the application); (c) the browser check: golden path, fa and en, desktop and 375 px, console and network clean; (d) any manual check ID (M-n) the task added or touched; (d2) the very large suites left to the end-of-sprint QA: the broad render suite `dotnet test PEMS.Tests --filter "FullyQualifiedName~PEMS.Tests.Web"` (7 to 11 minutes, 640+ tests, only the SQL test `DynamicSidebarSqlTests` red on `main`), the full `dotnet test PEMS.slnx` and the SQL families, written as `not done - end-of-sprint QA` on this task's own checklist and, when the change touched a shared layout, resource file or stylesheet, the guard classes of [chapter 05](05-environment-and-commands.md) "Test budget" that the session did not run; (e) for a docs-only or design task, the human read-through of section 6.
- **Open owner decisions are lines too** (`open - owner decides: <question>, default <value>`), and so is every part of the *Done when* that is not met yet (`open - <what is missing>`), so the issue says what remains until Done.
- **The issue is self-contained.** From the Jira issue alone a reader must see: what was merged (PR, commit), what was run (counts), every line still open and why, and which follow-up issues exist. If the issue stays In Progress because only a first step is merged, post the same checklist as a draft and say which lines belong to which step.
- A checklist with a line marked `not done` is complete; a checklist that omits what the author could not run is incomplete (section 1a, point 5).

## 2. Who and where

- **Who:** a person other than the author: the owner, the other member, or a named tester. An AI agent may write the checklist and drive a browser to collect evidence, but the verdict
  on work an agent produced is given by a person.
- **Where:** `main` at the merge commit, run locally (`PEMS_ENV=local`, [chapter 05](05-environment-and-commands.md)), or `staging` when the owner has promoted `main` to it (a push to `staging` deploys: only on the owner's request).
  Record the commit hash and the environment in the report.
- **Accounts:** one per role the task touches (`tools/TestAccountProvisioner`), never the real administrator.

## 2a. Tests and review are one step (for now)

Owner decision 2026-10-26, until a CI gate exists (plan row #7): the local test run is **line 1 of every QA checklist** ([README.md](../../README.md) "Local tests"), done by the tester together with the UI checks.
- An author who can run the tests does so before the merge and writes the counts in the report; the tester repeats the run (line 1).
- An author in a cloud session installs the SDK first ([chapter 05](05-environment-and-commands.md) "Cloud sessions") and runs everything that does not need SQL Server (build, database-free tests, drift gate). Only the tests that need SQL Server may be reported as not run: the author lists their exact commands and the failure reason, merges, and moves the issue to In Review; line 1 then carries the first SQL run.
- **Done needs both**: line 1 green (only the known failures of README.md "Local tests" may stay red) and all other lines Pass. A red test is a defect like any other: `qa-failed`, back to To Do, fix by a new PR.
- When CI runs the tests on every merge, line 1 becomes "CI run on the merge commit is green" and this section is removed.

## 2b. Time-boxed tests in a session (owner decision 2026-11-03)

An author runs what is quick and meaningful and does not wait for what is slow or impossible; the rest goes to the checklist (section 1b), never silently dropped.

- **Run before the merge (minutes):** `dotnet build PEMS.Web` (Razor compiles every view), `dotnet test PEMS.UI.Tests` (components, tag helpers, golden manifests, script contracts, the adoption ratchet, the guideline registry test), and the page and render tests of the views the change touched (recipes in [chapter 05](05-environment-and-commands.md) "Test recipes"). Fix every failure that is not on the known list.
- **Run every test you can; leave the very large ones to the end-of-sprint QA (owner decision 2026-11-04).** Do not skip a test because it is tedious: run the build, the UI tests, the guard classes and the exact classes of what you touched (`python tools/test-gates/gates.py` picks them from your changed files), every one that fits the budget below, and report the counts. A **very large suite** (the whole `PEMS.Tests.Web` namespace, the full `PEMS.Tests` / `PEMS.slnx`, the SQL Server families) is **not run by you**: the QA of the sprint runs them once at the end for all the tasks that are In Review, so a session never spends minutes on them per task. **Checks are not combined between tasks:** every task keeps its own checklist line d2 with the exact command, marked `not done - end-of-sprint QA`, and its own result; no task is marked as "covered by" another.
- **Test budget: two minutes per command (owner decision 2026-11-04, learned on 2026-11-04 when a "page tests" run took 11 minutes and another 4 minutes for six SQL failures).** A command a session starts must be expected to finish in about two minutes. Use **exact class names** in the filter (`FullyQualifiedName~CmmsListPagesTests`), never a word or a namespace: `~Letter` also runs `LetterConcurrencyTests` (SQL Server, each case fails after a 15-second connection timeout), `~PEMS.Tests.Web` is 640+ rendering tests (7 to 11 minutes), `~Api` is fine (about 15 seconds) only as the namespace `PEMS.Tests.Api`. Measured costs and the safe classes are in [chapter 05](05-environment-and-commands.md) "Test budget". If a run needs more than the budget, do not start it: it is a line of the QA checklist (below).
- **A merge never waits for a test the session cannot run (owner decision 2026-11-03).** Run the quick gates, merge, move the issue to In Review with `qa-pending`, and put every test or check that was not run as an unchecked line of the QA checklist; the tester runs them after the merge and the issue goes to Done or back to To Do with `qa-failed` (section 1a, section 4). Nobody holds a pull request "until the browser check" or "until the SQL tests"; a failing check found later is a defect of the issue, fixed by a new pull request.
- **Browser checks are part of the QA checklist, always (owner decision 2026-11-06).** Every issue whose change can be seen in the UI (a view, a component, a script, a stylesheet, a resource text) has, in its Jira QA checklist, a **browser-check section**: one unchecked line per page or flow, each saying **which page (route or menu path), what to do, and what must be seen** (for example "Letter details: open the Return dialog; the header shows the title and a close button, the footer shows Cancel and Return"). Rules: (1) the author writes these lines even when an AI agent will never open a browser, and never leaves them out because the change is "mechanical" or "output unchanged"; (2) when the session did run a browser check, the line is checked and carries the evidence (screenshot name or URL); when it did not, the line stays unchecked and says `not run - <reason>`; (3) an issue delivered in several slices keeps **one consolidated browser-check list** (slice number in front of each line) in the last QA comment, so the tester opens one list; (4) the issue does not move to Done while a browser line is unchecked, and a failed line becomes a `qa-failed` finding (section 5a of guideline 00). A pull request description repeats the list in one line ("Not run: browser check of ...").
- **Test tiers (owner question 2026-11-06, SCRUM-393):** (1) every task: build, UI tests, the guard classes and the exact classes of the files you touch (`gates.py` picks them); (2) a cross-cutting batch (changes `PEMS.UI`, `wwwroot` or more than about 20 views, because the Web tests pin view and script source text): also the whole `PEMS.Tests.Web` family, once per PR, in the background, without `DynamicSidebarSqlTests` (about 1 minute); (3) end of sprint: the SQL families, the full solution and the browser checks. Measure before optimising: `dotnet test ... --logger "trx;LogFileName=x.trx"` gives a time per test; the first run found one class holding 82% of the minutes.
- **Do not run, and list as `not done - <reason>`:** the SQL Server tests (names with Sql, LiveDb, Concurrency, Migration, Numbering, Atomicity, Retry, RealSql), the whole `PEMS.Tests.Web` namespace unless the change is cross-cutting (see "Test tiers" below; 53 s since 2026-11-06, was 8 minutes), the full `dotnet test PEMS.Tests` run (without SQL Server it stalls for more than ten minutes: do not start it), the HTTP smoke tests, and every browser check (themes, fa and en, dialogs, forms posting). Each line names the exact command or the page and the expected result, so the tester runs it without asking.
- **A failing test that needs SQL Server is not a result:** report it as `not run - no SQL Server`, and check that none of the failures is in a view, layout or component test. A failing test in markup is always fixed, never listed away.
- **Only a test the session cannot run, or that is very slow, waits for the end-of-sprint bulk review (owner decision 2026-11-05, clarified the same day).** A test that cannot be run by the author on this machine (no SQL Server, a missing tool, a service that is down) or that takes too long for the time budget is not retried, not pulled in through a wide filter and not run again hoping it flips: write it as an unchecked QA line with the exact command and the reason (`not run - no SQL Server`) on every task it concerns, so the tester runs all of them in bulk after the doing tasks of the sprint are finished, and run it again before that only if it is seen to pass elsewhere or the owner says it is fixed. **This never covers a test that fails because of a bug or bad code:** such a failure (a view, a component, a tag helper, a service, a wrong expectation caused by the change) is fixed in the same task and the test stays in the run; it is never excluded, skipped, listed away or left for the bulk review. When unsure whether a failure is environmental, read its message: a connection timeout or a missing file is environmental, a wrong value or markup is a bug. Use exact class names so a wide filter does not drag environment tests in; if a wide run was unavoidable, name the environment failures in the recap and treat every other failure as yours.
- **Check first whether a test is doable, then decide (owner decision 2026-11-05).** Never start a test to find out that it cannot run. `python tools/test-gates/gates.py` runs a preflight before it lists anything: it asks the machine whether the SQL Server tests can run (a local SQLEXPRESS instance, Integrated Security, as the disposable-database guard demands) and prints `CAN` or `CANNOT` with the reason. `CAN`: the slow and SQL classes that mention your files run in a step of their own, with the others. `CANNOT`: they are written at once as unchecked QA lines `not run - <reason>`, with the exact command. The same rule holds for any other environment need (a tool, a service, a browser): check it in a second, then run or list. The guard itself is never loosened to make a test run (it protects the real databases); that is an owner decision.
- **Only SQL-safe changes without SQL Server:** a session that cannot run the SQL tests changes views, components, scripts, documents and plan rows only. A change to the schema, a migration, a query, a transaction or a service that touches the database waits for a session with SQL Server, or is split into its own task whose line 1 is the SQL test run.
- **A stalled or slow tool is not a failed job:** a command moved to the background keeps running; read its result before retrying, and check the state of a merge or push before repeating it (GitHub API timeouts can hide a command that succeeded).

## 3. "Fully in the UI"

Every step is done through the browser exactly as an end user or administrator would: no SQL, no command line, no API calls, no reading of code.
Set-up that has a screen (users, roles, settings) is done on that screen. If a step can only be done outside the UI, that is a finding (Instructions rule 20 requires licensing, installation,
update and version operations to be UI-completable) and is recorded as a defect or, for infrastructure work, as a named exception.

## 4. Procedure

1. **Prepare (10 min).** Read the issue (*Done when*), the PR description and the Test Plan rows of the backlog row. Fresh browser profile; open the console and network tab.
2. **Complete the checklist** the author drafted when moving to In Review (section 1a; write it yourself if it is missing, and tell the author): one line per *Done when* item, plus the standard lines below.
   **Do not copy steps that already exist: refer to them** (section 5a). If the task introduces a manual check or a local test, add it to the right existing README (never a new file) and refer to it from the checklist.
3. **Execute in the browser** and mark each line Pass / Fail / Blocked with evidence (screenshot file name, Test Plan case id, or the URL of the rendered page).
   Line 1 is always the local test run (section 2a). Standard lines for any UI change: golden path; one edge case and one invalid input; every role that must be allowed and one that must be denied; **fa (RTL) and en**;
   **desktop and 375 px**; reload and back-button state; console and network free of errors; two neighbouring screens still work; keyboard focus and Escape on dialogs.
4. **Defects.** Each failure becomes a Jira issue of type Bug (or a one-line comment if trivial) that goes through the normal task flow ([chapter 00](00-task-lifecycle.md) section 3a), linked to the task; set `qa-failed` (replacing `qa-pending`), add the defect list as a comment and move the task **back to To Do**; it keeps its assignee and all QA comments. The fix is a new PR to `main` and the task returns to In Review. Retest only the failed lines and their neighbours.
5. **Pass.** Set `qa-passed`, add the result comment, update the Test Plan row (`Needs QA` -> `Passed` with date and tester) in a small PR to `main`, and move the issue to Done.
6. **Time-box.** Effort S: 15-30 minutes; M: about 1 hour; L: split into sessions. QA that finds the checklist cannot be executed is a defect in the task description.

## 5. Templates

**QA checklist comment**
```
QA checklist - <issue key> - commit <hash> - environment <local|staging> - tester <name> - <date>
| # | Check (from Done when / standard) | Result | Evidence |
| 1 | Local tests green; only the known failures stay red (README.md "Local tests") | Pass/Fail/Blocked | <counts, console output file> |
| 2 | <Done when item 1, as a user action and expected result; refer to README steps> | | <screenshot / case id> |
| 3 | Golden path fa + en | | |
| 4 | Role allowed / role denied | | |
| 5 | 375 px and desktop | | |
| 6 | Console and network clean | | |
Verdict: qa-passed | qa-failed - defects: <keys>
```

**Tests are lines of the checklist, and the author pre-marks what was run** (owner decision 2026-10-27). Every automated test that proves a *Done when* item gets its own line (class or filter, expected count) next to line 1, and a mechanical proof (a green and a red pipeline run, a mutation run) gets a line too. The author fills the `Result` column only for lines the author really ran, in the form `Pass (author, <date>)` or `Fail (author)` with the evidence (counts, run link, commit); every line not run says `not done - <reason>`. The tester re-runs the pre-marked lines that are cheap (line 1 always) and records `Pass (tester, <date>)`; a line the author could not run stays open until a tester runs it. Because a posted checklist is never edited (section 7), the author adds the marks as a new comment "QA checklist - author results" that repeats the table with the results filled in, and later rounds repeat it again.

## 6. Tasks without a screen (docs, plan, CI, design)

The check is a read-through **in the UI that shows the result**: the rendered Markdown in the PR "Files changed" view, the Jira issue, the workflow run page, the board.
Checklist lines: each *Done when* item found; links and tables render; no secret value, internal address or personal data; the text agrees with the guideline and the plan row;
numbers and names are consistent between documents. Record it in the same template.

## 7. Keep the record

The "QA checklist" and the QA result comments stay on the Jira issue **after Done** (and after the issue is closed): they are organisational knowledge for the next release, the next tester and audits.
Never delete, overwrite or collapse them; correct a mistake with a new comment that says what changed. The PR description keeps the same text. Re-run an old checklist when the area changes again.

## 7a. Sprint review procedure (owner decision 2026-11-06)

A sprint is closed by one review of everything that is In Review, not by closing issues one by one. The words are those of guideline 00 section 0.0 (sprint, issue, slice, follow-up). The first review is `docs/qa/SPRINT_1_REVIEW_QA.md`. This section (7a) is the procedure of the **first** sprint and stays as it was run; the sprints after it follow section 7b.

1. **Freeze (the day before the end).** All work of the sprint is merged; every issue that is merged is In Review with `qa-pending` and a QA checklist (section 1a). An issue that is merged but still To Do or In Progress is moved to In Review now. Nothing new is started in the sprint.
2. **Audit (the agent, one query).** List the issues of the sprint (`sprint = <id>`) with their comments. Per issue write down: status, label, the last QA checklist, every unchecked line, every sentence that says "not run", "not done", "needs a browser" or "owner decision". Search the other open issues before creating anything (rule 28).
3. **Sort what was found.** (a) **Work that is not done** (code, a missing component, a decision that needs a build) becomes a **technical debt issue in the next sprint**: Jira issue with the epic, labels `area-*`, `doer-*`, `effort-*`, `plan-<n>`, the title `[#n] ...`, a plan row (`plan_sync.py new`), and a link to the issue it came from; an open issue that already covers it is commented instead of duplicated. (b) **Checks that were not run or never defined** go into the two QA tasks (step 4). (c) **Owner decisions** go into the section "Owner decisions" of the QA tasks. (d) **Re-audit rule (owner decision 2026-11-06).** After the audit, re-audit the sprint once more, looking only at the issues that are really In Review or Done. A gap becomes a technical debt issue in the next sprint **only if** it is truly new: it was found in the work of those issues AND no open issue (backlog or sprint) already covers it (search first, rule 28; an overlapping issue is commented and linked, never duplicated). A gap that is not technical debt of the closed sprint (a wish, a future feature, something noticed in passing) is defined **only in the backlog**, with no sprint. Each new issue says which of the two it is.
4. **Two identical QA tasks in the closing sprint**, one for each tester (Hamid and Saber), both assigned, both in the sprint, with the same body: the step-by-step checklist, written from step 2 and from the README "Manual checks in the UI" (reuse the M-numbers; a check that was needed but not defined gets a new M-number in the README). Sections: A prepare the environment, B automated runs that need SQL Server, C live infrastructure and process, D browser checks by area (each line: page, action, expected result; the matrix of languages, themes and widths is stated once), E owner decisions, F documents to read, G close. Each issue's own checklist stays as it is; the QA tasks do not replace it, they run it.
5. **Run it.** Each tester goes through every line and writes `Pass`, `Fail (SCRUM-n)`, `Blocked (reason)` or `N/A (reason)` with the evidence. A line that needs access the tester does not have is `N/A (no access)`, never skipped silently. Both testers do the whole list (two pairs of eyes), the agent may drive a browser to collect evidence but never gives the verdict (section 2).
6. **Failures are Bugs in the active sprint** (owner decision 2026-11-08, replacing the decision of Saber of the same day that sent them to the next sprint; confirmed 2026-11-10). Each `Fail` becomes an issue of type **Bug** (guideline 00 section 3a) in the **active sprint**, with the epic, the area label, `qa-failed`, the steps and the expected result, a plan row made at creation (guideline 00 section 5d), and a link from the QA tasks. In Sprint 1 the closing sprint is still the active sprint until step 7, so the Sprint 1 review Bugs live in Sprint 1; for later sprints see section 7b. The issue whose line failed is not Done until its Bug is fixed and the tester who found it has re-checked the line. The fix goes through the normal flow (PR, merge, In Review).
7. **Close.** When both QA tasks have no `Fail` or `Blocked` line left (`Pass` or `N/A` with a reason and an owner): every issue of the sprint becomes **Done**, its checklist is marked checked with a comment "Checked by sprint review QA SCRUM-<keys>", `qa-pending` is removed, the QA tasks are Done last, and the sprint is completed in Jira (issues that are not Done move to the next sprint with a reason). A `Blocked` line that cannot be resolved moves to a named issue of the next sprint before the sprint can be completed.
8. **Rules.** Every known Bug belongs to the active sprint (chapter 00 section 3a step 2); none is left in the backlog. Nobody marks an issue of the sprint Done before step 7. An `N/A` always has a reason and a name. The review result (commit under test, counts of automated runs, number of lines Pass, Fail, Blocked, N/A) is a comment on each QA task. After the review, update the guideline with anything durable (chapter 6).

9. **Sprint goals now (owner decision 2026-11-06).** Sprint 2: finish the componentized work, build the form engine, the page engine and the other engines, and move the data layer to JSON files; it also carries the technical debt of Sprint 1. Sprint 3 (planned): the JSON files move to database tables. Keep the sprint goal in Jira in step with this line.

## 7b. Sprint review procedure for the sprints after the first (owner request 2026-11-10)

The Sprint 1 review was one 84-line task run in full by two people (2 h 35 m of tests, 26 Bugs, a description at Jira's size limit, evidence spread over 13 comments). It was right for a first sprint with 98 issues that nobody but their author had checked. From Sprint 2 on, the review is smaller, split and mostly generated. Steps 1 to 3 of 7a (freeze, audit, sort, re-audit rule) stay; steps 4 to 7 change as follows.

1. **Per-issue QA is the main check.** Each issue is checked by someone other than its author when it is merged (sections 2 and 4), not at the end of the sprint. The review at the end covers only what is still unchecked, plus a smoke list. The target at freeze is: no In Review issue without a checker and a date.
2. **The tests run once, on a machine that is not in use.** Tier 3 (section 6) runs after the freeze on a clean checkout, family by family (UI tests, Web family, each SQL family, the rest), by the agent or CI, once; the counts and failures go in one comment. Testers do not repeat it. Timing tests that fail under load are re-run alone before they are called red (guideline 00 section 3b class 8). The commands of the checklist are tried on a second machine before the sprint (for example `sqlcmd` needs `-C` with ODBC Driver 18, and the SQL instance may be `.` or `.\SQLEXPRESS`).
3. **One review task per tester, with different lines** (not two identical copies): the lines are split by area so each area is checked once, and each tester also re-checks a sample of about 20% of the other's passed lines and every security, permission and money flow. The two tasks share one checklist file under `docs/qa/` and one results table.
4. **The checklist is generated, not written.** `docs/qa/SPRINT_<n>_REVIEW_QA.md` is built from (a) the unchecked lines of the QA comments of the In Review issues (the audit, step 2 of 7a), grouped by area, and (b) the **smoke list**: the 20 to 30 flows that must always work (sign in, change password, open each sidebar module, create and save one record per module, the notification bell, the search palette, one Excel export, one upload and preview, language and theme switch, the 375 px shell), kept in the README "Manual checks in the UI" and extended whenever a Bug shows a flow that was missing. The Sprint 1 sections A (environment), E (owner decisions) and F (documents) become short: the environment is five checked lines, owner decisions go in the sprint planning note, documents are read when they change.
5. **The environment is prepared once and written down.** A copy of `PEMSDB` restored from a COPY_ONLY backup as `PEMSDB_QA<n>` (never the working database), the test users per default role created by a script (their passwords stay with the tester, not in Jira), an SMTP sink on 127.0.0.1, the commit under test. The first line of the task is "environment ready" with these facts.
6. **The matrix is sampled, as decided on 2026-11-07:** every browser line is run in Persian, Light, desktop; English, Dark, Turquoise and 375 px are run on a sample of pages (the shell, one list, one form, one details page, one modal), named in the task.
7. **Evidence goes in comments, one comment per section, never in the description.** The description holds the checklist (kept small); each result is `Pass`, `Fail (SCRUM-n)`, `Blocked (reason)` or `N/A (reason)`. The summary table (counts per section) is the last comment.
8. **Bugs are in the active sprint and each has its plan row at creation** (7a step 6, guideline 00 sections 3a and 5d). The review runs in the **last three days** of the sprint so the active sprint can still absorb the fixes; a sprint is completed at its end date. An issue whose line failed stays In Review and moves with its Bug to the next sprint, which is then the active sprint; every other issue of the sprint becomes Done with the comment "Checked by sprint review QA SCRUM-<keys>".
9. **After the review, update the guideline once**: add the new defect classes to guideline 00 section 3b and the new smoke lines to the README, and say in the review comment what was added.
