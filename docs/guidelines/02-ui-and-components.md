## 1. The core rule: call and modify, don't re-write [R26]

> Do **not** hand-write a new form control, table, modal, badge, empty state, KPI card or page header inside a page.
> **Find the existing component, call it, and modify it** (parameters, options, slots, a new variant) for the new need.
> If it cannot express the need, **extend the component first** (in the library, with docs and tests), then use it.

Decision order, every time:

1. Is there a component/partial/View Component/template for this? -> use it as is.
2. Does it almost fit? -> add a parameter/variant to the shared component (backwards-compatible for existing callers), update its catalog entry and tests, then call it.
3. Is it truly missing? -> add it to the library (`PEMS.UI` once it exists; until then the shared partials in `Views/Shared` and the shared CSS/JS) following section 4, then call it. Mention it in the Jira comment.
4. Only if 1-3 are impossible: page-local markup with a written reason in the task comment. CI ratchet counts raw markup; the numbers may only go down.

**Library-first protocol for agents (owner decision 2026-11-02; no exceptions, no "just this once").** Hand-written Bootstrap markup is never an acceptable answer to a UI task. Before you write any `<input>`, `<select>`, `<textarea>`, `<button>`, `class="btn`, `badge`, `alert`, `card`, `modal`, `nav-tabs`, `progress`, `accordion`, `list-group`, `spinner`, `<table>` or a status/KPI block:

1. **Search the library first**: the registry table below, `PEMS.UI/TagHelpers/*.cs` (`grep -rn "HtmlTargetElement" PEMS.UI/TagHelpers`), `PEMS.UI/Components/*.razor`, then `PEMS.Web/Views/Shared`. If a `pems-*` tag helper or component covers the block, call it.
2. **If it almost fits, modify the component, safely**: add an option or a tag attribute with a default that keeps today's output byte for byte (the default is what existing callers get); add a `ControlState`-style plain C# class if it computes classes; add a unit test of the new output and keep the existing golden tests green; re-record only the manifests that really changed (`PEMS_GOLDEN_RECORD=1`, then `git checkout` the line-ending noise); lower the ratchet baseline; add the row to the registry below and a line to the CHANGELOG. Never fork a second component and never copy markup "to adapt it".
3. **If it is missing, add it to the library first** (options record, component, tag helper, manifest, sample, tests, registry row), then use it from the page. Nothing is added to a view before the component exists.
4. **A tag helper cannot express it** (a boolean Razor expression in a control attribute, markup built in a JavaScript string, a date picker that does not exist yet): keep the page markup, record the reason in the Jira comment and the list of exceptions of that adoption issue, and open or extend the library task that will remove it. The ratchet baseline must not grow.
5. **Prove it**: `dotnet build PEMS.Web` (Razor compiles the views), `dotnet test PEMS.UI.Tests` (includes the ratchet and `GuidelineRegistryTests`), and the web tests that read the touched pages. A page test that depends on attribute order is wrong, fix the test, not the component.

**Component inputs and names (owner decision 2026-10-27).** A component takes **one light-weight object with named properties**, never positional arguments: `new ButtonOptions { Label = "Save", Tone = Tone.Danger }`, not `new ButtonOptions("Save", Tone.Danger)`. Options are `sealed record` types with `init` properties (`required` for what must be given), so they are immutable, vary with `with`, deserialize from the same JSON a database row will hold, and cost the same as a constructor call (no performance effect; the render-time test in `PEMS.UI.Tests` stays green). Use the same property name for the same idea in every component:

| Idea | Name | Idea | Name |
| --- | --- | --- | --- |
| visible text of a button, badge, field, option | `Label` | heading of a state, view or form | `Title` |
| second line of explanation | `Description` | technical or secondary reason | `Detail` |
| help under a field / hint inside it | `HelpText` / `Placeholder` | link target | `Href` |
| colour meaning / size | `Tone` / `Size` | a call to action (link with `Label`, `Href`) | `Action` |
| icon-font class | `Icon` | on/off flags | `Required`, `ReadOnly`, `Disabled`, `Sortable` |
| what a field or column is | `Kind` | identifies a field / column / definition | `Name` / `Key` / `Id` |

**Component manifest (SCRUM-433).** Every registered component carries `@attribute [PemsComponent("<key>", Category = "...", Icon = "bi-...")]` and gets a machine-readable manifest generated from its code (`ComponentManifestGenerator`, `ComponentManifestCatalog`): key, category, icon, message key `component.<key>` (no visible text in the component), the JSON Schema of its options (from the options records; texts accept a string or a language map; unknown properties are rejected) and a sample. Stored options JSON is validated with `ComponentManifestCatalog.Validate(key, json)` (field errors with JSON Pointer and constraint code) and turned into parameters with `ToParameters`. A new component needs the attribute, a sample in `ComponentSamples`, and its approved snapshot in `PEMS.UI.Tests/Manifests` (record with `PEMS_GOLDEN_RECORD=1`); a test fails when any of them is missing.

Registry and JSON keys are the component name without the `Pems` prefix, in kebab-case (`empty-state`, `error-state`, `loading-state`, `button`, `badge`). A new component reuses these names; add a new name here only when no existing one fits. (The Titan project's component names are not in this repository; if the owner supplies that list, align the table to it before the next component.)

Where components live **today**: `PEMS.UI` (registry below; `PEMS.Web` references it and finds its views and `_content/PEMS.UI/` assets automatically), plus the `_PageHeader` adapter, `.vs-*` workspace CSS and `pems-ui.js` in `PEMS.Web`; the Light and Dark `--pems-*` tokens live in `PEMS.UI/wwwroot/tokens.css` (Turquoise: still `site.css`/`pems-glass.css`, task SCRUM-476).
Search `PEMS.Web/Views/Shared`, `wwwroot/css`, `wwwroot/js` before building anything. Once `PEMS.UI` ships (plan #319-#334), it is the only place; this chapter then shrinks to "use PEMS.UI".

## 2. Rules for new and changed UI [R26, D6-D8]

- No inline `style=`, no inline `<script>`/`<style>`, no inline `onclick`, no CDN or external URL, no hex colours: use `var(--pems-*)` tokens.
- Logical CSS only (`margin-inline-start`, `inset-inline-end`, `text-align:start`) so one stylesheet serves RTL and LTR; handle directional icons/transforms explicitly.
- **Texts in `PEMS.UI` components are inputs** ([ADR-0008](../../plan/adr/0008-component-texts-are-inputs-translatable-text.md)): label, help, placeholder, option, header, title, empty text, button text and error are `TranslatableText` parameters (JSON map of language slug to text, e.g. `{"fa":"ذخیره","en":"Save"}`), never literals or defaults in the component. A test fails the build when a literal word appears in a component. Resolve and format only through `IPemsLocale`. **Data is never translated, only formatted** (owner decisions 2026-10-27: Persian pages show Jalali dates and Persian digits, English pages ISO dates and Latin digits; nothing else for now). Formatting is for display only: a value a user types, posts or stores is never rewritten (`DataEntryUnaffectedTests`), and input fields carry ISO dates and Latin digits. Numbers and dates are **bound** by one binder (`PEMS.UI.Binding`, registered in `PEMS.Web` Program.cs): a Persian page accepts `12.5` as a browser posts it and Persian digits typed by the user; never add per-page parsing of numbers or dates (SCRUM-421). Pages in `PEMS.Web` that do not use a component yet keep localization keys (`SharedResource`); dates are Jalali in the UI (stored UTC/Gregorian).
- Component contract is technology-neutral: describe fields/columns/views as **descriptors** so the same component can be rendered from code today and from metadata tomorrow (dynamic forms/modules). Do not hard-wire a screen to one entity when a descriptor can express it.
- Use standard behaviours: loading state, empty state, error state, validation messages next to the field, state preserved on row actions (filters, sort, page, tab) - see the UI engineering standard sections 3-5.
- Popups/dropdowns/lookups: follow the portal and stacking rules; never patch `z-index` per page.
- Accessibility: labels bound to inputs, keyboard reachable, visible focus, `aria-*` on custom widgets, sufficient contrast.
- Responsive: verify at 375 / 600 / 768 / 992 / 1366 px in EN and FA when touching layout or positioning.
- JavaScript: initialise idempotently (`dataset.pemsInit`), unbind global listeners on close, namespace everything, `fetch` with antiforgery header and visible error handling.

## 3. Modifying an existing component safely

1. Find all callers (grep the partial/tag/CSS class). Note how many pages depend on it.
2. Add the new behaviour behind an optional parameter or variant; default output must stay byte-identical for old callers. **Prove it with a golden-output test** (`PEMS.Tests/Ui/SharedPartialsGoldenTests.cs`, files in `PEMS.Tests/Ui/Golden/`): record the HTML of the unchanged code with `PEMS_GOLDEN_RECORD=1`, make the change or move the file, and the test must pass without re-recording. Moving a partial between projects follows the same rule (`git mv`, keep the view-model namespace, no caller edits).
3. Update the component's documentation (states, RTL/LTR example, accessibility note) and tests.
4. Check at least two existing callers in a browser after the change.
5. If the change alters defaults for everyone, that is a separate Jira issue with the user's approval.

## 4. Adding a component (when 1.3 applies)

A component is done only with: documented states (default, hover, focus, disabled, loading, error, empty), RTL + LTR example, accessibility statement, localization keys, token-only styling, tests, a catalog entry, and no dependency on the page it came from. Fix shared components once - never patch page by page.

## 5. Verifying UI work

Run the app, open the page in a browser, exercise the golden path and one edge case, in `fa` and `en`, desktop and mobile width; read the console (no errors) and network (no external hosts). Report what you saw. If you could not run it, say so - do not claim it works.

## 6. Dynamic builders (forward look)

Form/module/workflow designers are embedded JavaScript components inside Razor pages [D1]. Anything the designers produce renders through the **same** components as hand-built pages. Therefore: any component you build today should accept data-driven configuration, not just compile-time Razor parameters.

**Descriptor-driven navigation components** (owner/agent decision 2026-11-06, SCRUM-484 and SCRUM-485): `PemsTabs`, `PemsBreadcrumb`, `PemsMenu`, `PemsStepper` and `PemsSidePanelNav` are rendered from data through `PemsDescriptorHost`, for the BPMS renderer and the designers; they are registered, tested and kept even where no hand-written page calls them. Hand-written pages use the tag helpers `<pems-nav>`, `<pems-dropdown-menu>` and `<pems-crumb-trail>`. Do not delete a descriptor component because it has no page caller.

## 7. The UI component registry: one door, the registry key (ADR-0013, SCRUM-506)

**Rule (owner decision 2026-11-05): every component is created, used, modified and removed through the registry.** Create = a component with a `UiKeys` constant, a registry row and a facade. Use = a `pems-*` tag (or a descriptor) that names the key; no view, controller or script instantiates a component type, writes a component's markup or renders it with a type of its own. Modify = change the component behind its key (default output unchanged, golden manifest and ratchet green) and never fork it under another name. Remove = unregister the key, remove its facade and rows in the same pull request. A component that is not in the registry does not exist for pages, descriptors, the designer or the graph.

Views and descriptors reach a component the same way: by its key (`UiKeys`, registered in `PemsComponentRegistry`, rendered by `IPemsComponentRenderer`). Rules that keep this from drifting:

1. **Keys are constants.** Use `UiKeys.X`; never write a key as a string literal in code (the registry itself registers with the constants).
2. **Every `pems-*` tag helper declares `[PemsFacade(...)]`**: `UiKeys.X` when it renders that registered component through the renderer, `FacadeKind.Part` for a child tag that only hands its content to its parent's component. There is no third kind (no "native", "exempt", "framework" or "direct" facade): a tag helper that extends an ASP.NET Core one (input, select, textarea, label, validation summary) lets the framework helper compute the model-bound values (name, id, value, errors, options) and the registered component writes the element. A **new** tag helper is `UiKeys.X`: add the component first (section 4).
3. **Adding a component is one step**: the component, a `UiKeys` constant and its registry row, the facade, the row in section 1 of this chapter, a test. `UiRegistryDriftTests` fails if any of them is missing or if `UiKeys` and the registry differ.
4. **Nothing writes its own markup any more** (SCRUM-507 finished 2026-11-06: 60 of 60 tag helpers render a registered component or are a part of one). `FacadeKind.Direct` was removed from the code, so a tag helper that writes its own markup does not compile, and `UiRegistryDriftTests` pins the kinds to Component and Part. Never bring a "temporary" kind back; the remaining hand-written markup lives in views and scripts and is counted by the adoption ratchet (item 8, SCRUM-508).
5. **Graph**: `python tools/graphify/update.py` adds one node per key with edges key -> component, key -> facade and view -> key, so `graphify query "who uses badge"` works.
6. **Converting a tag helper to a component, the recipe** (SCRUM-506; first done for `info-grid`, `info-item`, `kpi-tile`): (a) `PemsX.razor` + an options record in `PEMS.UI/Components` with the same markup the helper wrote, attribute for attribute; (b) `UiKeys` constant, registry row, `ComponentSamples` row (a component with a second parameter such as `Empty` wraps its sample as `{"options":{...}}`); (c) the helper takes `IPemsComponentRenderer`, passes the page's class and attributes (`BlockTagHelper.PageClass`, `PageAttributes`) and renders `RenderAsync<PemsX>`, `[PemsFacade(UiKeys.X)]`; (d) record the golden manifest (`PEMS_GOLDEN_RECORD=1`, then restore snapshots you did not touch), add the key to `ComponentManifestTests` and a row to section 1 of this chapter; (e) the existing output tests stay as they are and only build the helper with a renderer, so any byte of difference fails; (f) the registry, drift and golden tests must stay green. A key an extension pack or a test fixture uses is renamed in the fixture, built-in keys are never overridden.
7. **Every batch is create-then-convert** (owner decision 2026-11-05): first create the batch's components in the registry (recipe a-b), then convert the code that wrote the markup to use them (c), never the reverse and never a tag left half-way. A batch is not merged with a half-converted family unless the task row lists the rest as a later batch. Anything new that needs markup (a view, a script template, a descriptor, a form-control variant) is a component with a key first. When a rule here is unclear, the stricter reading wins; a rule change goes through the owner and is recorded here and in ADR-0013 in the same pull request.
8. **"Every piece of the UI is a component" (owner decision 2026-11-05).** The border of the UI is the front end as it would be if it were split off behind a RESTful API: every view, partial, layout, tag helper, script that builds markup, stylesheet rule that styles a hand-written block, inline script and style belongs to it, and each piece is a component with a key in the registry (or is removed). The adoption ratchet counts what is left; a pattern without a ratchet entry is not "allowed", it only has no counter yet: add the counter with the component. The backlog for it is **never cancelled**: a task about this work is modified, merged into a neighbour or split, and a gap gets a new task (guideline 00 section 1, item 5e: search Jira first). The ratchet baseline only goes down. **Round 2 counters (SCRUM-509 to 512, 2026-11-06; all at 0)**: `form` (`<pems-form>`), `raw-button` (`<pems-button tone="bare" css="...">`), `on-handler` (inline `on*=` attributes become `data-pems-click|change|submit` actions handled by `pems-actions.js`: print, back, prevent, submit-form, call, toggle-hidden, toggle-class, check-all), `style-block` (`<style>` blocks go to a stylesheet), `raw-input` (`<pems-input kind="bare">`; hidden data inputs are not counted) and `dom-builder` (a script never creates a visual element with `createElement`: it clones a template of the `script-templates` component, sets `shell` (library scripts: confirm dialog, error toasts, command palette, skeleton, sidebar search ...) and the page sets). Not counted by `dom-builder`: `createElement` of `script`/`link` (loading a resource), `option` (use `new Option` or `PemsTemplate.options`), `input` (a hidden data field or a file picker) and `a` (a download trigger). The script scan covers `PEMS.UI/wwwroot/*.js` for the two markup counters.
