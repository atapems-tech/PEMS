## ۳. قرارداد مشترک نهایی (توجیه‌شده با شواهد بالا)

```csharp
// PEMS.Web/Models/StageDiagramViewModel.cs
public enum StageItemState { Pending, Current, Done, Rejected }

public class StageDiagramItem
{
    public string Label { get; set; } = "";
    public string IconCssClass { get; set; } = "";
    public string? RoleLabel { get; set; }   // Nullable - طبق تفاوت واقعی WorkOrder (بند ۲)
    public StageItemState State { get; set; }
}

public class StageDiagramViewModel
{
    public List<StageDiagramItem> Stages { get; set; } = new();
}
```

### چرا این فیلدها و نه بیشتر

| فیلد | چرا در قرارداد است |
|---|---|
| `Label`, `IconCssClass` | در هر سه پیاده‌سازی مشترک و اجباری |
| `RoleLabel` (Nullable) | فقط در ۲ از ۳ - **طبق دستور صریح («اگر فیلدی فقط برای یک مصرف‌کننده لازم است، آن را به‌زور به قرارداد عمومی اضافه نکن») باید Nullable باشد، نه اجباری** - همین‌جا رعایت شد |
| `State` (enum ۴ مقداره) | جایگزین ترکیب `currentIndex` + یک پرچم سراسری `isRejected`/`isPendingResubmission` که **قبلاً داخل هر Partial محاسبه می‌شد**. طبق بند ۶ دستور این فاز («فراخوان‌کننده باید وضعیت از‌قبل‌تعیین‌شده را بدهد؛ Partial هرگز State را محاسبه نکند»)، این محاسبه (که کاملاً دامنه‌محور است - EDMS یک قانون «همه‌چیز بعد از currentIndex رد‌شده است» دارد، VDR قانون «فقط خودِ currentIndex» دارد) **به همان View مصرف‌کننده منتقل شد، نه به داخل Partial مشترک** |

### فیلدهایی که عمداً حذف شدند

- **بنر هشدار (Banner):** نه در قرارداد است، نه در Partial رندر می‌شود. چون محتوای آن
  (متن دقیق + `<strong>` تو در تو در EDMS) کاملاً دامنه‌محور و در ۲ از ۳ متفاوت است، این
  Markup **دقیقاً در جای قبلی خودش (بالای فراخوانی Partial، داخل همان View)** باقی ماند -
  بدون هیچ تغییر. اضافه‌کردن این به قرارداد مشترک نیازمند یا `Html.Raw` (ریسک نامتناسب با
  سود) یا شکستن به چند فیلد جدا (پیچیدگی نامتناسب) بود - طبق بند ۳ دستور («اجتناب از تحمیل
  فیلدی که فقط یک/دو مصرف‌کننده لازم دارند»).
- **DbContext/سرویس/بررسی مجوز:** هیچ‌کدام در هیچ نسخه‌ی قبلی وجود نداشت که نیاز به حذف
  داشته باشد - Partial از همان ابتدا Stateless بود.

## ۴. حفظ تفاوت‌های معنایی (اثبات خط‌به‌خط)

هر دو مصرف‌کننده‌ی مهاجرت‌شده با ردیابی دستی، شرط‌به‌شرط، در برابر منطق اصلی تأیید شدند:

**EDMS:** `isRejected && i > currentIndex ? Rejected : i < currentIndex ? Done : i == currentIndex ? Current : Pending` -
دقیقاً همان زنجیره‌ی ternary اصلی (`isRejected && i > currentIndex ? "rejected" : i < currentIndex ? "done" : i == currentIndex ? "current" : ""`)
با نگاشت یک‌به‌یک `""` → `Pending`.

**VDR:** منطق دو-مرحله‌ای (اول تشخیص `isBranchedRange`، سپس تصمیم داخل/خارج آن بازه) عیناً
از شرط اصلی
(`isPendingResubmission && i >= currentIndex && key != "Planned" && key != "Check" ? (i == currentIndex ? "rejected" : "") : i < currentIndex ? "done" : i == currentIndex ? "current" : ""`)
بازتولید شد - با تست دستی روی ۳ نقطه‌ی بحرانی (`i` قبل از/برابر/بعد از `currentIndex` در حالت
`isPendingResubmission=true`) تأیید شد که خروجی یکسان است.

**رنگ رابط بین‌مرحله‌ای (Connector):** قانون اصلی هر دو (`i < currentIndex ? "done" : ""`)
با یک قانون کاملاً محلی و بدون‌State-سراسری در Partial جدید بازتولید شد: *«رابط بعد از
مرحله‌ی i سبز است اگر‌و‌فقط‌اگر State مرحله‌ی i برابر Done باشد»*. برای هر دو پیاده‌سازی،
این قانون با ردیابی دستی چند نقطه (ازجمله نقاطی که مرحله‌ی i در بازه‌ی رد‌شده قرار دارد)
تأیید شد که همیشه با فرمول اصلی هم‌ارز است - چون در هر دو پیاده‌سازی اصلی، «رد‌شده» و «Done»
هرگز هم‌زمان روی یک مرحله صادق نبودند.

**آیکون:** قانون اصلی (`done → check-lg`, `rejected → x-lg`, else → آیکون خودِ مرحله`) بدون
تغییر در Partial جدید پیاده شد، فقط شرط از رشته‌ی `cssClass` به مقدار enum `State` تغییر
کرد.

## ۵. مرز مجوز

**بدون تغییر - صفر.** نه نسخه‌ی قبلی، نه نسخه‌ی جدید، هیچ‌کدام `IPermissionService`/
`ICurrentUserService`/`IAccessControlService` را نمی‌بینند. هر سه ورودی (`Label`,
`IconCssClass`, `RoleLabel`, `State`) از پیش توسط View مصرف‌کننده (که خودش از Controller/
ViewBag می‌گیرد) محاسبه می‌شوند. **هیچ مجوز جدیدی افزوده نشد، هیچ بررسی مجوز موجودی حذف
نشد** - چون این Partial از ابتدا هیچ ارتباطی با لایه‌ی مجوز نداشت.

## ۶. مرز گردش‌کار

منطق تعیین `State` (که واقعاً دامنه‌محور و متفاوت میان EDMS/VDR است) **هرگز به داخل Partial
منتقل نشد** - دقیقاً همان‌جایی ماند که بود (داخل بلوک `@{ }` بالای هر View مصرف‌کننده)، فقط
از یک ساختار محلی (`cssClass` رشته‌ای) به یک ساختار صریح‌تر (لیست `StageDiagramItem` با
`State` enum) تبدیل شد. **هیچ قانون گردش‌کار جدیدی اختراع نشد؛ هیچ قانون موجودی حذف نشد.**

## ۷. دوزبانگی و RTL/LTR

- بدون تغییر در استراتژی - `Label`/`RoleLabel` همچنان رشته‌های از‌قبل‌ترجمه‌شده (Hardcoded
  انگلیسی/فارسی، دقیقاً مثل قبل) هستند که View مصرف‌کننده تأمین می‌کند؛ Partial هیچ منطق
  زبانی جدیدی ندارد.
- **تأیید مستقیم:** `grep` در کل `wwwroot/css/` نشان داد **هیچ فایل CSS خارجی (ازجمله
  `admin.rtl.css`) هیچ Override‌ای برای کلاس‌های `pems-wf-*`/`pems-wo-*` ندارد** - یعنی تمام
  استایل این نمودارها همیشه فقط در همان `<style>` درون‌خطی زندگی می‌کرده، نه در جایی که این
  فاز ممکن بود از قلم بیندازد.
- ترتیب مراحل (چپ‌به‌راست در DOM) دست‌نخورده ماند؛ چرخش بصری زیر `dir="rtl"` همچنان کاملاً
  از رفتار پیش‌فرض Flexbox (`display:flex`، بدون `flex-direction` صریح) می‌آید - دقیقاً
  همان مکانیزمی که هر سه پیاده‌سازی قبلی هم به آن متکی بودند. **این فاز این رفتار را تغییر
  نداد، فقط آن را حفظ کرد.**

  کلاس/سرویس جدا منتقل شد - یعنی این منطق همچنان **قابل‌تست‌شدن مستقیم با یک تست واحد
  نیست** (دقیقاً همان وضعیت قبل از این فاز - هیچ تستی هم قبلاً این منطق را پوشش نمی‌داد).
  این فاز یک زیرساخت تست جدید برای این منطق نساخت، چون آن خودش یک بازطراحی معماری
  (استخراج منطق از View به یک کلاس تستی) بود که صریحاً خارج از دامنه‌ی این فاز است.
