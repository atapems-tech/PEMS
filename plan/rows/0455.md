## Evidence

Follow-up of #434. Every save of a published definition adds a version of up to 1 MB. Owner decision 2026-10-28: retired versions are kept FOREVER (the version table is the history, because the payload text is not in the audit trail), so nothing is pruned; the growth must at least be visible. Cache behaviour (hits, stamp reads) is invisible today.

## Prompt

1) A size and growth report (rows and bytes per kind, per month, the largest definitions and the ones with most versions) on the definition manager (#449) and in the support bundle (#174). 2) Cache statistics (hits, misses, stamp reads) in the health dashboard. 3) A setting Definitions__RetainRetiredVersions with the single supported value 'forever' (documented in env/README.md) so a later retention policy is a code change in one place, not a surprise; no pruning job is built; any other value stops the start-up with a clear message (fail closed). The other retention options and the rules a future policy must obey are in docs/architecture/METADATA_REGISTRY_DESIGN.md section 9. 4) A warning in the report when the definition tables pass a configurable size (default 1 GB) so an administrator decides before the database is a problem. 5) Tests.

## Requirement

Done when: the report shows rows, bytes and growth per kind and the heaviest definitions; cache statistics are visible; the size warning appears above the configured size; no code path deletes a definition version (a test asserts it); all covered by tests.
