## Evidence

Each module reports errors in its own way (a page summary, a thrown message, a flash text), so clients and the form components cannot render or test them uniformly. RFC 9457 defines application/problem+json and leaves the validation list to an extension member; ASP.NET Core can produce problem details natively. 2026-10-28: follows the REST API standard ADR-0009 / guideline chapter 08 (#431).

## Prompt

1) Define the response: status 400 or 422, type, title, detail and an 'errors' array where each item has field (JSON pointer), constraint code (for example min, max, maxLength, pattern, required, notUnique), message key, parameters and the localised text. 2) Implement it once (AddProblemDetails and an exception/validation filter) and use it for the generic engine, the API and import. 3) Stable constraint codes documented in the catalog (#355) so UI and tests depend on codes, not on text. 4) Settings for the maximum number of errors and the maximum nesting depth. 5) The form components of #357 and the import report of #360 render this one shape. 6) Never leak internal details, stack traces or SQL in the response.

## Requirement

Done when: an invalid API call, form post and import row all return the same structured errors in the user's language; codes are stable and listed; a test fails if a module returns a different shape.
