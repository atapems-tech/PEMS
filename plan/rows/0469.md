## Evidence

Error paths are the least tested paths; code in an error page can itself throw (Microsoft guidance) and a leaked message is found only by accident. Nothing today forces an error class and checks what the user sees. The guideline has an API standard (chapter 08) but no standard for how errors are raised, mapped, logged and shown.

## Prompt

1) Write the guideline chapter 09 (error handling): taxonomy, who maps, what a user sees, what is logged, the trace id rule, forbidden patterns (swallowing, ex.Message to users, generic throw) and a review checklist; link it from the lifecycle chapter. 2) Test suite with forced failures: each taxonomy class through a page and through /api, database down, dependency timeout, concurrency conflict, unique violation, start-up failure, the error page itself failing; assert status, shape, language, trace id and the absence of stack, SQL text, file paths, ex.Message and framework versions (a response scanner reused by every controller test). 3) Add error-path cases to the QA procedures (chapter 07) and to the security review (OWASP testing guide: improper error handling). 4) Monitoring hook: count of 5xx per route in the log with an alert threshold as a setting. Sources: OWASP Error Handling Cheat Sheet (one global handler, generic user messages, no stack traces, 5xx only for server failures, monitor 5xx); Microsoft Learn ASP.NET Core error handling (UseExceptionHandler and IExceptionHandler, status code pages, ProblemDetails, error pages must not throw, start-up errors are only visible to the host); RFC 9457.

## Requirement

Done when: the chapter is merged and referenced; the suite covers every class and runs in CI; a deliberately leaking handler fails the build; the QA checklist has the error-path steps.
