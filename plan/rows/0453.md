## Evidence

Gaps left on purpose by #435 and #434 (guideline chapter 08, rules 7, 9, 10): the Idempotency-Key store is in memory, per server and lost on restart, so a retry after a restart or on a second server creates a duplicate; cursor paging is specified for exports and very large tables but not built; single reads answer 304 only on the discipline pilot, not on definitions.

## Prompt

1) Durable idempotency store: a table (key, user, request fingerprint, status, location, ETag, body, expiry), a filter/helper used by every create (disciplines, definitions, import), expiry cleanup (background job), same behaviour: replay returns the first response, a different body with the same key is 422; concurrent same-key requests wait or get 409. 2) Cursor paging: opaque cursor (limit, no total) in ApiListQuery and a first export endpoint (definitions list or audit export) that pages past 10,000 rows; conformance and Spectral rules for it. 3) If-None-Match/304 on GET one and ETag on lists of definitions. 4) New migration; settings in env/*.env; guideline chapter 08 updated.

## Requirement

Done when: a create replayed after an application restart and on a second instance returns the first response without a second record; an export endpoint pages 50,000 rows by cursor with stable order; GET of a definition with a matching If-None-Match answers 304; tests, conformance suite and OpenAPI snapshot updated.
