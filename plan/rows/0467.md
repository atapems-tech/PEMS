## Evidence

Audit 2026-10-29 of views and scripts: 40 fetch( calls with 46 .catch( (no shared handling), 10 alert( calls, one global error handler. Failed requests are reported differently per page and never reach the server log. A comparable platform wraps the UI in an error boundary that shows a reference code, offers Try again and Reload and posts the error to the backend; its weakness is that the browser reference and the server reference are different codes.

## Prompt

1) One fetch wrapper in PEMS.UI: antiforgery header, timeout, abort on navigation, parse problem+json (#363, guideline 08), map status to a message key, retry only idempotent requests with backoff, offline detection. 2) Global capture of window.onerror and unhandledrejection; a rendering fallback for dynamic pages (PageHost, #438) that shows the trace id with Try again and Reload and never loses unsaved form input. 3) Replace the 10 alert( calls with the Toast/Alert component (#324) showing the message and the trace id (copy button). 4) Report endpoint: authenticated, rate limited, size limited, fields whitelisted, no personal data, own server only (offline), writes to the error store of #465 with the same trace id the failing request carried. 5) Accessible announcements (role alert, focus) per WCAG 3.3.1; CI ratchet for new alert(. Sources: OWASP Error Handling Cheat Sheet (one global handler, generic user messages, no stack traces, 5xx only for server failures, monitor 5xx); Microsoft Learn ASP.NET Core error handling (UseExceptionHandler and IExceptionHandler, status code pages, ProblemDetails, error pages must not throw, start-up errors are only visible to the host); RFC 9457.

## Requirement

Done when: a failing request on any page shows one consistent toast with a trace id; the same id finds the log entry; a script error shows the fallback without losing input; the alert( count is zero and guarded.
