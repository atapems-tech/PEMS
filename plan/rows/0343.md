## Evidence

A customer whose production server is offline must be able to recover a lost administrator password with the vendor's help, without a back door in the product and without any remote access. The licence flow already proves that file exchange works offline; the reset reuses its shape with its own key. Gate: this row can start only after #342 (licence flow end to end) is Done. Independent of the separate administrator-recovery work done by Saber (second-admin reset, one-time recovery codes, server-side break-glass, shared audit/notification/session revocation): that work does not wait for the licence flow and this row does not block it; this flow plugs into it as the optional vendor-assisted recovery path, which must stay off until the customer enables it. 2026-10-28 plan audit: dependency/milestone corrected (see docs/audits/2026-10-28-dynamic-restful-audit.md).

## Prompt

Write docs/design/ADMIN_RESET.md (no secrets). Flow (same shape as licence activation, all in the browser UI; no terminal or CLI step): 1) the customer opens the administrator recovery page on their installation and downloads a reset request file (.pemsrstreq: Install ID, fingerprint hash, licence id, product version, account, random nonce kept server-side as a pending request, signed by the install key); 2) the customer sends the file to us; 3) in the developer/owner UI we upload it, the tool verifies the signature, matches it to the customer and licence in the ledger, we confirm the customer, enter the reason and the identity check, and download a reset response file (.pemsreset) signed with the separate reset key and bound to the request nonce, licence id, Install ID, purpose and expiry; 4) the customer uploads the response file on the same page and the password reset form opens; the pending request is consumed so the file works once. Decide: reset-key custody. Decided 2026-10-25 by the owners: the licence key and the reset key are each created and used only on the owner computers (the own computers of Hamid and Saber, who are the owners and the developers; also called developer-local or owner machines), as the last step of the licence and reset flows. Neither key is ever in the assistant's environment, on a shared or CI server, or in the repository. The reset key is still a different key from the licence key. To settle in the ADR: whether the keys stay offline (encrypted external drive) between uses, where the backup copies are and who holds them, what the reset changes (password; MFA/passkeys and sessions as in the shared recovery rules), expiry of the response file, rate limits, audit on both sides, behaviour on a cloned or re-hosted machine (#104, #116). AFTA check (to be confirmed with the testing lab through #184): no default, master or hard-coded password and no standing vendor credential; the vendor can act only on a request that the installation itself generated, for one installation, once and for a short time; the capability is off by default and enabled explicitly by the customer administrator; every use is audited, all administrators are notified, the account sessions are revoked and the event goes to the SIEM feed; the reset key is separate from the licence key and can be revoked through an update; everything works offline by file exchange, so no remote access to the customer server is ever needed. Validity: the response file expires after a period the owner chooses in the developer UI when the file is issued: default 1 day, allowed range 1 to 7 days in whole days, and no unlimited or open-ended option (the tool refuses values outside the range and the product checks the limits again, so a correctly signed file with a longer validity is rejected). The pending reset request on the customer side expires on the same bounds. AFTA: a short, bounded, single-use validity fits the check recorded here; the 1-day default and the 7-day maximum are to be confirmed with the testing lab (#184), and if the lab wants a shorter maximum the limits change in one setting without changing the file format.

## Requirement

Done when: an approved ADR with the file formats' fields, the key-custody details on the owner computers, the threat model (replay, wrong customer, tampered or forged file, cloned machine, clock change, leaked file) and a written AFTA compatibility assessment accepted by the security consultant; #344-#349 are written against it. The validity rule (default 1 day, range 1 to 7 days, no unlimited option) is confirmed by the AFTA assessment.
