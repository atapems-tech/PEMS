## Evidence

Without a settings surface the format hierarchy of #366 stays code-only; users in an Iranian company expect to switch calendar and digit style themselves, and designers need to see the effect of a format before saving.

## Prompt

1) Admin page for system defaults and per-app/per-model settings; the field properties panel of the form designer (#44) gets Format next to Validation, with presets, a custom pattern where allowed, and a live preview that shows sample values formatted and an input that is parsed and validated against both. 2) User profile page: calendar (Jalali/Gregorian), digit shape, number style, time zone, week start, language (links to #207). 3) Permission to change system and model settings, audit of every change, versioned with the metadata package (#23). 4) Settings cached with invalidation (#28). 5) Accessible and RTL-correct controls built from PEMS.UI components. Best-practice sources: W3C Internationalization (date and number formats follow the language context, avoid ambiguous numeric dates, support non-Gregorian calendars, keep localisation separate from translation); MDN notes on input type=number (locale separators and non-ASCII digits are sanitised, no pattern support, so formatted or Persian input needs type=text with inputmode); ISO 8601 for stored dates; Unicode CLDR through Intl (browser) and ICU/CultureInfo (server); OWASP: validate the canonical form, one normalisation policy.

## Requirement

Done when: an administrator changes a model's date and number format and sees it in lists, forms and exports without a deploy; a user switches calendar and digits for themselves; every change is audited; the designer preview shows formatted, parsed and validated values.
