## Evidence

Formatting in PEMS is done page by page: 377 hand-written date and time format strings in 138 views using 12 different patterns, 217 number format strings, 103 native date, 8 datetime-local and 137 number inputs whose look follows the browser locale, and Jalali support in only 6 files. Existing rows #24, #205, #206, #208 and #209 ask for translated labels, Persian digits, the Jalali calendar and fixed reports, but nothing defines where a field's format lives or how it relates to validation. Dates are stored and shown inconsistently; native date inputs ignore the Jalali calendar, 12 different display patterns exist, and a native date control cannot be switched to Jalali.

## Prompt

1) Canonical forms: a date without time is stored as a date-only value (ISO 8601, no time zone, so a due date never shifts a day), an instant as UTC; the user's time zone is applied only for display and input of instants, daylight saving included. 2) Choose a maintained library for calendars and conversion (evaluate the .NET PersianCalendar and the browser Intl calendar support first; for the picker evaluate maintained Jalali date libraries; avoid unmaintained or deprecated packages; works offline; record licences in L_OSS). 3) Display presets from #366 (Jalali long and short, Gregorian ISO, weekday names, Saturday as week start), Persian digits optional. 4) Input: a date picker component in PEMS.UI showing Jalali or Gregorian per setting, with typed entry parsed tolerantly (separators, Persian digits, two-digit years rejected or expanded by a documented rule) and invalid dates such as 1403/12/30 in a non-leap year rejected with a suggestion. 5) Server and client use the same conversion tests. 6) Ranges and relative windows from #355 evaluate in the same calendar-independent canonical form. Best-practice sources: W3C Internationalization (date and number formats follow the language context, avoid ambiguous numeric dates, support non-Gregorian calendars, keep localisation separate from translation); MDN notes on input type=number (locale separators and non-ASCII digits are sanitised, no pattern support, so formatted or Persian input needs type=text with inputmode); ISO 8601 for stored dates; Unicode CLDR through Intl (browser) and ICU/CultureInfo (server); OWASP: validate the canonical form, one normalisation policy.

## Requirement

Done when: a date picked as Jalali is stored as the correct Gregorian date-only value and shown back identically on every page; date-times display in the user's time zone across a daylight-saving change; invalid Jalali dates are rejected with a hint; the picker works in RTL and LTR and offline; views no longer carry their own date format strings (ratchet).
