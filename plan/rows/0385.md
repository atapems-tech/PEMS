## Evidence

Owner requirement 2026-10-27: after a merge into staging or demo the migration must really run, otherwise the application crashes. The deploy polls /health/database for UpToDate, and #383 stops a chain that fails on SQL Server before upload, but UpToDate does not prove the newest migration of this commit is applied, a failed start-up migration stops the app, and no tested way back exists. 2026-10-27 after #262 (SCRUM-280, merged): the rollback procedure with the automatic pre-update backup and a restore test now exist (CODE_FIRST_DATABASE.md "Rollback"), so only the proof and the failure mode remain here.

## Prompt

1) Post-deploy proof: the pipeline compares the newest applied migration id with the newest migration of the deployed commit and fails with both ids. 2) Safe failure mode: a failed or newer-than-build database leaves the app up in a maintenance state (static page, /health/database 503 with state name, failed attempt in DatabaseUpdateRuns); check every migration runs in a transaction and list the exceptions. 3) The pipeline run summary prints the previous good commit and links the #262 rollback steps. 4) Tests, README check.

Scope extension 2026-10-29 (rule 28): the readable start-up failure report (logs/startup-error.txt) and the static maintenance page are specified in #464; this row's pipeline step prints that report when /health/database does not answer, and the post-deploy check stops after repeated 5xx answers (done in deploy-site.yml 2026-10-25).

Scope extension 2026-11-05 (owner: the migrator runs automatically whenever it is needed, with no manual step, in every environment; rule 28, extends #309 which is In Review as SCRUM-327): 5) Trigger rule, written down and tested: on every start the migrator compares the applied migration history with the build: empty database -> install; behind -> update; equal -> no-op; ahead of the build -> never touched, maintenance state (item 2). Database__MigrateOnStartup stays true in every env file; opting out (false) is explicit and shows on the Admin Database Update page. 6) One migrator at a time: a SQL application lock (sp_getapplock, fixed resource) so two instances (scale-out, an IIS overlapped recycle, a deploy while the old site still runs) never migrate at once; the others wait with a timeout and serve the maintenance state, never crash. 7) Unattended safety: transient errors retried only for the connection, one transaction per migration (exceptions listed), the pre-update backup per Database__BackupBeforeUpdate (on wherever data matters: production and uat today, decide for staging and demo), the destructive-operation guard of #384, the result in DatabaseUpdateRuns, a readable failure (#464). 8) One path for every trigger: module and definition update packages (#284, #170) and the definition store call the same migrator, no second path. 9) Test: two hosts started against one empty database and against one database that is N migrations behind show exactly one migrating and the other reporting up to date; a restart is a no-op.
