## Evidence

Exports are a second place where formats drift: strings instead of typed cells cannot be sorted or summed, and a comparable platform shipped an invalid-date defect in downloaded reports and layout overflow in PDF exports. 2026-10-28 plan audit: dependency/milestone corrected (see docs/audits/2026-10-28-dynamic-restful-audit.md).

## Prompt

1) The export service of #210 asks the formatting engine for display text where text is wanted, and writes typed cells (number, date, boolean) with matching Excel number-format codes where the user will calculate; Jalali display is a cell format or an extra column, the stored date stays a real date. 2) CSV: canonical values by default (ISO dates, dot decimals) with an option for display format. 3) PDF and print use the same formatters, the user's language and direction, and wrap LTR tokens correctly. 4) Header labels use the translated field labels. 5) Tests that open a generated file and check cell types, values and an invalid-date regression. Best-practice sources: W3C Internationalization (date and number formats follow the language context, avoid ambiguous numeric dates, support non-Gregorian calendars, keep localisation separate from translation); MDN notes on input type=number (locale separators and non-ASCII digits are sanitised, no pattern support, so formatted or Persian input needs type=text with inputmode); ISO 8601 for stored dates; Unicode CLDR through Intl (browser) and ICU/CultureInfo (server); OWASP: validate the canonical form, one normalisation policy.

## Requirement

Done when: an Excel export sorts and sums numbers and dates correctly and shows Jalali dates as configured; CSV defaults to canonical values; PDF text, direction and dates match the screen; the invalid-date regression test passes.
