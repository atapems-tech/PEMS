## Evidence

Owner requirement 2026-10-28: publishing a retired version again (rollback) must be possible or not depending on a compatibility precheck. Today rollback (#434) only re-validates the payload shape: an old form version may no longer fit the data entered since (a field added later holds values the old version does not know; a type was widened and new values do not fit the old type), or may reference definitions that were removed.

## Prompt

1) A precheck endpoint POST /api/v1/definitions/{id}/actions/precheck-rollback {toVersion} (dry run, no change) and the same check inside rollback: run the compatibility analysis of #457 from the currently published version to the retired one against today's stored data and today's referenced definitions (#450). 2) Verdict: allowed, allowed with warnings (listed), or blocked (reasons with counts and samples, for example 'N records hold values in field X that version 2 does not have'); blocked rollbacks return 409/422 problem+json with the report; an administrator may acknowledge warnings, never override a data-loss block. 3) allowedActions and the manager screen (#449) show the verdict per retired version before the button is pressed. 4) The automatic rollback of #457 uses the same check for the version it returns to and, if that one is also unsafe, stops and raises an alert instead of looping. 5) Tests incl. a retired version that is blocked by newer data and one that is allowed.

## Requirement

Done when: for each retired version the API says whether it can be published again and why not; a blocked rollback changes nothing; an allowed one publishes as before; the manager screen shows the verdict; tests cover blocked, warning and allowed.
