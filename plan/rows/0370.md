## Evidence

Row #24 stores translatable strings in metadata; nothing defines how they are resolved in a context or how mixed-direction text (codes, e-mail, URLs, numbers inside Persian sentences) is displayed. W3C: keep localisation separate from translation. 2026-10-28 plan audit: dependency/milestone corrected (see docs/audits/2026-10-28-dynamic-restful-audit.md).

## Prompt

1) Resolution order for every visible string: field setting -> model language -> app -> user preference -> system default, with a documented fallback to the default language and a visible marker in the designer when a translation is missing. 2) Direction: set dir per field and per value type; wrap LTR tokens (codes, e-mail, URLs, Latin words, numbers with units) in directional isolates so punctuation and order stay correct inside RTL text, and keep the zero-width non-joiner rules of #364. 3) Display rules for empty values, booleans, option labels (translated, with the stored code unchanged), long text (truncate with tooltip, never cut mid-grapheme) and optional transforms (upper case for codes). 4) Report of missing and untranslated strings per language, usable in CI. 5) Tests with mixed-direction samples. Best-practice sources: W3C Internationalization (date and number formats follow the language context, avoid ambiguous numeric dates, support non-Gregorian calendars, keep localisation separate from translation); MDN notes on input type=number (locale separators and non-ASCII digits are sanitised, no pattern support, so formatted or Persian input needs type=text with inputmode); ISO 8601 for stored dates; Unicode CLDR through Intl (browser) and ICU/CultureInfo (server); OWASP: validate the canonical form, one normalisation policy.

## Requirement

Done when: the same label shows in the right language for field, model, app and user contexts with a defined fallback; mixed-direction samples render correctly; a CI report lists missing translations; option labels change without touching stored values.
