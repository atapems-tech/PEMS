## Evidence

Persian text arrives with Arabic Yeh/Kaf instead of the Persian letters, Persian or Arabic digits, zero-width non-joiners and invisible bidi marks; without one policy the same name or code is stored in several forms, breaks uniqueness and search, and length checks count characters differently. OWASP: validate the canonical form, apply one normalisation policy before validation, storage and comparison, cap sizes before parsing, avoid regular expressions prone to catastrophic backtracking, treat a timeout as a failure.

## Prompt

1) Write the policy in the catalog (#355): Unicode NFC, Arabic Yeh/Kaf to Persian Yeh/Kaf, digits to ASCII for numbers and codes (keep the display digits as a presentation setting), trim and collapse spaces, remove or reject zero-width and bidi control characters except the zero-width non-joiner inside Persian words, per-field switch for exceptions. 2) Implement one normaliser used by the validator (#356), the import (#360) and the search; store the normalised form for unique keys and keep the original for display where needed. 3) Regular expressions: whole-value match, bounded input length, match timeout (the .NET regex timeout parameter or a non-backtracking engine), a failed timeout is a rejection. 4) Limits as settings: request body size, JSON nesting depth, array length, string length before any parsing. 5) Tests with Persian samples, look-alike characters and a catastrophic-backtracking pattern.

## Requirement

Done when: the same Persian text typed with Arabic or Persian letters and digits is stored and compared as one value; a pattern that would backtrack catastrophically is stopped by the timeout; oversized or too deeply nested input is rejected before parsing; tests prove each case.
