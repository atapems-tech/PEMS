## Evidence

Formatting in PEMS is done page by page: 377 hand-written date and time format strings in 138 views using 12 different patterns, 217 number format strings, 103 native date, 8 datetime-local and 137 number inputs whose look follows the browser locale, and Jalali support in only 6 files. Existing rows #24, #205, #206, #208 and #209 ask for translated labels, Persian digits, the Jalali calendar and fixed reports, but nothing defines where a field's format lives or how it relates to validation. Money and quantities are formatted with 217 scattered format strings; type=number inputs show locale-dependent separators and reject non-Latin digits (the browser empties the value), so Persian digit entry silently fails.

## Prompt

1) One formatting service on the server (CultureInfo/ICU through one wrapper) and one on the client (Intl.NumberFormat), both driven by the format object of #366, so the same value looks the same in views, grids, reports and exports. 2) Digit shapes (Persian or Latin) and separators as settings, with the display digits a presentation choice only. 3) Money: decimal arithmetic, scale from the field, one documented rounding rule (half away from zero unless a field says otherwise), rial and toman conversion by scale and never by floating point. 4) Tolerant parser used for typing, paste and import: accepts Persian and Arabic digits, both separator styles, grouping marks, a leading minus or parentheses, and returns the canonical decimal or a parse error. 5) Formatted inputs use type=text with inputmode and keep the raw value; type=number is not used for money or formatted values (MDN caveats). 6) Replace the page-level ToString format strings through the audit of #359 and a ratchet. Best-practice sources: W3C Internationalization (date and number formats follow the language context, avoid ambiguous numeric dates, support non-Gregorian calendars, keep localisation separate from translation); MDN notes on input type=number (locale separators and non-ASCII digits are sanitised, no pattern support, so formatted or Persian input needs type=text with inputmode); ISO 8601 for stored dates; Unicode CLDR through Intl (browser) and ICU/CultureInfo (server); OWASP: validate the canonical form, one normalisation policy.

## Requirement

Done when: one service formats and parses numbers on server and client with identical results for the shared fixtures; Persian digit entry works in every numeric field; rial and toman amounts are exact; views no longer carry their own number format strings (ratchet in CI).
