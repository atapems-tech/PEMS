## Evidence

Formatting in PEMS is done page by page: 377 hand-written date and time format strings in 138 views using 12 different patterns, 217 number format strings, 103 native date, 8 datetime-local and 137 number inputs whose look follows the browser locale, and Jalali support in only 6 files. Existing rows #24, #205, #206, #208 and #209 ask for translated labels, Persian digits, the Jalali calendar and fixed reports, but nothing defines where a field's format lives or how it relates to validation. A comparable implementation shows the risks: one hard-coded locale in its date component, date strings built without zero padding, an invalid-date defect in downloaded reports and a deprecated date library for the Jalali picker. 2026-10-28 plan audit: dependency/milestone corrected (see docs/audits/2026-10-28-dynamic-restful-audit.md).

## Prompt

1) For each type in #11 define three things: the canonical value that is stored and exchanged (ISO 8601 date-only for dates, UTC instant for date-times, decimal with fixed scale for numbers and money, normalised text), the display format, and the input and parse format. 2) Presets with examples (date: Jalali long/short, Gregorian ISO; number: grouping, decimal separator, digit shapes Latin or Persian; currency: rial, toman, symbol position, negative style; percent; units; boolean: yes/no, tick; empty value: dash). 3) Where a format lives: a settings hierarchy system -> app -> model -> field -> user preference with a defined fallback (a model or field setting wins for content, the user's setting for chrome), stored in the metadata registry as a versioned format object next to the validation object. 4) Label-related formats: label, help, placeholder, error and option text as translatable strings (#24), unit and prefix/suffix, direction. 5) State the pipeline order and the rule that validation always runs on the canonical value. 6) Write docs/architecture/FIELD_FORMAT_CATALOG.md and an ADR. Design rule (decided here, applies to #355-#365): formats and validations are designed together in one field descriptor and one test suite, but kept as separate layers of one pipeline: raw input -> parse by input format -> canonical value -> normalise (#364) -> validate the canonical value (#355/#356) -> store canonical -> format for display. Validation never runs on a display string, and a display format never changes what is stored. Best-practice sources: W3C Internationalization (date and number formats follow the language context, avoid ambiguous numeric dates, support non-Gregorian calendars, keep localisation separate from translation); MDN notes on input type=number (locale separators and non-ASCII digits are sanitised, no pattern support, so formatted or Persian input needs type=text with inputmode); ISO 8601 for stored dates; Unicode CLDR through Intl (browser) and ICU/CultureInfo (server); OWASP: validate the canonical form, one normalisation policy.
