## Evidence

A format that cannot be parsed back, or a parse result that validation rejects although the user typed what was displayed, is a classic defect; the same fixtures must cover format, parse and validation together (design rule of #366).

## Prompt

1) Extend the fixture file of #361 with format cases: for each type, locale (fa, en), calendar (Jalali, Gregorian), digit shape, time zone (including a daylight-saving change) and rounding mode, the value, its display text and the accepted input spellings. 2) Properties: parse(format(v)) = v, format(parse(s)) = canonical display of s, validation outcome equals the expected one for the parsed canonical value. 3) Edge cases: Jalali leap years and 30 Esfand, 31 Shahrivar, month and year boundaries, very large and very small numbers, rounding ties, negative zero, mixed digit scripts, ambiguous numeric dates rejected. 4) Run on server and client from the same file; CI fails on any difference. Best-practice sources: W3C Internationalization (date and number formats follow the language context, avoid ambiguous numeric dates, support non-Gregorian calendars, keep localisation separate from translation); MDN notes on input type=number (locale separators and non-ASCII digits are sanitised, no pattern support, so formatted or Persian input needs type=text with inputmode); ISO 8601 for stored dates; Unicode CLDR through Intl (browser) and ICU/CultureInfo (server); OWASP: validate the canonical form, one normalisation policy.

## Requirement

Done when: the shared fixture file covers format, parse and validation for every type; server and client agree on every case; a broken formatter, parser or rule fails the build.
