## Evidence

Follow-up of #434. Only the kinds form and page can be stored; a kind that is not registered cannot be stored. The designers (#57 views, #20 menus, #439 pages, theme work #30) each need their kind registered with a payload schema, otherwise each invents its own validation. Data-source and action kinds belong to #437.

## Prompt

1) Kinds layout (regions and their rules; the shipped list/form/detail/dashboard layouts of #325 as System definitions through #448), view (ViewDescriptor shape), menu (generalises NavigationMenuItem, #20), theme (design tokens, #30). 2) Per kind: IDefinitionKind validator, generated JSON Schema (like the component manifest), a valid sample, a snapshot of the schema, reference extraction (menu-target, renders), limits. 3) Page kind: reserve a route prefix and refuse a route that would shadow a code route (ADR-0011 point 2), and validate layout keys against registered layouts. 4) A short guideline section 'Adding a definition kind' with the checklist (validator, schema snapshot, sample, permission, reference roles, tests). 5) Tests incl. a harness that every registered kind has a sample, a snapshot and validation errors with pointers.

## Requirement

Done when: layout, view, menu and theme definitions can be created, validated, published and rolled back through the API; the harness fails for a kind without a sample or snapshot; a page with a layout key that does not exist or a route that shadows a code route is refused with a pointer; the how-to is in the guideline.
