# Instructions

Standing instructions for the PEMS project

Apply these in every task even when the request does not restate them. Keep in sync with Memory; a rule changes only with the owner's decision.

| # | Rule | Description |
| --- | --- | --- |
| 1 | Offline execution | Production has no internet: no CDN, external call, telemetry or online licence/update check is allowed in the product. Any new library must run fully offline and not depend on an online source at build time. (The website and demo are online parts and are separate from the product.) |
| 2 | Library-first, with licence control | Before hand-building (expression engine, grid, workflow designer, rules, scheduler, PDF/Excel) check for a mature library. For commercial sale every library licence (copyleft, revenue thresholds, mandatory watermark) must be recorded in row L_OSS; an unsuitable library is replaced. Custom code only with a stated reason. |
| 3 | Engines once, not per module | Each shared capability (metadata, forms, workflow, access/RLS, events, reporting, licensing) has exactly one implementation; modules call it. Parallel concepts are forbidden. |
| 4 | No new static modules | From now on a new module is built first as metadata (form/view/workflow). If that is impossible, record the reason and the needed extension point in an ADR. A new static module without this record is not allowed. |
| 5 | Persian-first, English file | The product default language is Persian with RTL; displayed dates are Jalali with Gregorian/UTC storage. The plan files, code identifiers and ADRs are written in English. |
| 6 | Go forward, not backward-compatible | During development applied migrations are not edited; always add a new numbered migration/seed. No backward-compatibility shim unless a live customer needs it. |
| 7 | Task workflow | Before starting set the row to In Progress; afterwards commit separately with a version bump and CHANGELOG, then update Status/Report in this file as its own commit. Message format 'vX.Y.Z: description'. Never use 'git add -A'; stage only specific files. |
| 8 | Order of work: scope, plan, design, implement | (a) Everything the user said, including later clarifications; (b) update the backlog row before designing; (c) then design library-first with best practice; (d) then implement. |
| 9 | Three version numbers | System = CalVer (YYYY.MM.PATCH); components = SemVer; editing this file does not change a version. The component table is on the Read Me page. |
| 10 | Secrets and keys | No real secret, key or connection string in the repo or release package. The licence-signing private key and the reset private key are created and used only on the owner computers (Hamid's and Saber's own) and are never in the repo, on a CI or shared server, or in the assistant's environment (L_KEYS). |
| 11 | Licence active everywhere | Licence checks apply in all environments (a signed dev licence); no bypass flag may reach any package. Always-free surfaces come only from an allowlist (L_FREE). |
| 12 | Central RLS | No data path (list, search, report, export, API, AI) is without the central RLS filter; direct role-based checks are not allowed. |
| 13 | Claims only from Done | Sales material, website and demo claim only Done capabilities with acceptance tests. 'Done' without evidence (file:line, commit or test) is not allowed. |
| 14 | QA of Done rows | A Done row whose Test Plan status is 'Needs QA' is not yet trustworthy; test it before using it in sales. |
| 15 | Fix anti-patterns in scope | If work passes through clearly poor code, fix it within that scope; large or risky fixes get their own row. |
| 16 | Finish, then stop | Complete the current task with all its closing steps, then propose a short list of next tasks and wait for the owner's choice. |
| 17 | No customer-specific forks | Customer differences live only in the licence (edition, modules, limits, updates-until), configuration, customer metadata packages and extension packs. There are no per-customer branches or builds; every shipped package comes from a tagged release and is recorded in the customer registry (CV_REG). |
| 18 | Landing and demo are separate deployables | The landing website (main domain) and the demo (subdomain) share one host but nothing else: separate source (the landing website in its own repository pems-landing, the demo in the demo branch of the product repository), pipelines, deploy accounts, secrets, environments, monitoring and rollback. A deployment, reset or failure of one must never touch the other. Both are deployed by GitHub Actions; if the host is unreachable the pipeline publishes the artifact for a manual deployment that follows the same script. |
| 19 | PM confirmation | A row is Confirmed by PM only when the owner says so. Claude never sets the flag on its own initiative except to record a decision the owner has just given, and never clears it. Rows on Hold stay scheduled but are not started until the PM releases them. |
| 20 | UI-only operations | Licensing, installation, update and version-reporting operations, for the customer and for the vendor, must be completable in a UI (browser pages or the graphical installer and vendor tool). A command line may exist only as an optional extra for automation, never as the only way. |
| 21 | Supportability Matrix in every task | The Supportability Matrix page (plan/sheets/supportability-matrix.md) is updated in every finished task: add or change the rows for what the task makes supported (capability or limit, component, supported value, version, verifying backlog row). Builder limits and other supported values come only from this matrix. Record the matrix update in the task Report. |
| 22 | Every task touches six things | Memory (if something was learned), the plan file, the Supportability Matrix, Instructions (only if a rule changes), CHANGELOG and a commit. |
| 23 | Schema only through migrations | Owner decision 2026-10-22: the database is fully code-first. A new environment is installed and every release updated by the migrator (startup or Admin > Database Update); no hand-run SQL for schema setup or updates. Needed DDL that EF cannot model goes into a migration (migrationBuilder.Sql); superseded SQL moves to legacy-trash/, it is not deleted until the owner agrees. |
| 24 | Settings in env files, secrets apart, nothing hard-coded | Owner decision 2026-10-23: every setting lives in env/<name>.env, every secret only in env/<name>.secrets.env (git-ignored) or an environment variable, for local, docker, demo, uat and production-<customer>. No environment-dependent value (URL, host, credential, port, lifetime, culture, policy flag) is hard-coded in code; a new setting is added to every env file and read with Required*. Customer differences are the production-<customer>.env file and the licence (rule 17). |
| 25 | Plan, the issue tracker and code stay consistent | Owner decision 2026-10-23 (docs/process/PLAN_TRACKER_WORKFLOW.md): the Backlog # is the Plan ID and is stored in the tracker in a Plan ID field; the plan files contain no tracker-specific fields. The plan owns scope (title, priority, milestone, requirement, dependencies), the tracker owns status, assignee and sprint. Branches, commits and PR titles start with the issue key. The plan files change only by pull request (a row is one file in plan/rows, so parallel edits of different rows never conflict); plan-sync check must pass. |
| 26 | Components only for new UI | Owner decision 2026-10-23 (docs/design/COMPONENT_LIBRARY_PLAN.md): once PEMS.UI exists, new pages are built from its components and templates; raw form-control/table/modal/badge markup, inline styles, inline scripts and CDN references are not added (CI ratchet). A missing component is added to the library first. |
| 27 | Keep the Jira report current | Owner decision 2026-10-26: every task keeps its Jira issue report up to date while the work runs and when it ends, not only at the end. (1) At start: comment 'Started by <agent or person>' with the plan. (2) During the work: a short comment at every milestone, decision, blocker or change of scope (what is done, what is next, what blocks), and a comment before any hand-over or stop. (3) At the end: a closing comment with what changed, files, tests run and not run, PR link, evidence for each 'Done when' item and open items for the owner. The same text goes in the PR description. An issue without a current report is not moved to In Review or Done. Never put a secret value in a report (mask to two characters at most). |
| 28 | Study existing tasks before adding one | Owner decision 2026-10-26: before adding a task (backlog row and Jira issue) read the existing ones - search the backlog and Jira by area, files, goal and keywords, including Done and Hold rows. If an existing task covers the work or can absorb it, modify that task (extend What to do / Done when, update the plan row file, the Jira issue and a comment saying what changed and why) instead of adding a new one. Add a new row only when no task fits, and name the tasks that were checked in its Evidence. A new row keeps the next free Plan ID; held (Hold) tasks count as not open. |
